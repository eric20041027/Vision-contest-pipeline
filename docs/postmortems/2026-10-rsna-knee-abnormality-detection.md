# 2026 RSNA Knee Abnormality Detection：vcp 實戰賽後報告

> **定位**：這份報告記錄 vcp 在一場真實 Kaggle 比賽裡的用法：它記到了什麼、哪裡斷了、哪些缺陷因此被修掉，以及對 1.0 的意義。不談模型技巧。
> **證據**：數字在 2026-10-30 從比賽工作區的台帳、run 紀錄與 vcp log 直接讀出（唯讀，沒有跑任何會寫 log 的命令）；工作區不在本 repo。
> 只能從筆記轉述、無法再驗的數字標 Ⓤ。依慣例，本文不放本機路徑、平台帳號、提交編號、他人的 notebook 或資料列。

## 1. 比賽與工作方式

- **比賽**：RSNA 膝關節 MRI 異常偵測，Kaggle code competition。提交的是 notebook，平台在隱藏測試集上重跑後計分；最後由參賽者在平台上勾選兩發作為最終成績。2026-10-22 23:59 UTC 截止，6,425 隊 Ⓤ。
- **工作方式**：
  - 一張消費級 GPU、一台 Windows 機器。
  - 2026-09-24 起兩條 AI 代理工作線並行：一條做影像模型、Kaggle 推論與提交，另一條做標籤研究。
  - 自訂每日上傳上限 3 發（`submit.yaml` 的配額，不是平台的限制）。
  - 台帳只有一個寫入者（提交那條線）；共用台帳（0.12.0 的 `ledger: shared`）沒有啟用。
- **規則**：每個自己訓練、要送出的模型都要有 vcp run 卡；公開 notebook 的元件先登記成不訓練的「登記 run」，再以 probe 身分送出。

### 名詞

| 詞 | 意思 |
|---|---|
| run 卡 | vcp 為每次訓練寫的紀錄（`run.yaml`、`train.yaml`）：資料、切分、程式碼狀態、環境、checkpoint 的 SHA |
| valA／valB／holdout | 自己切出的驗證子集；holdout 是 sealed（封存）子集，要明確解封才能讀 |
| candidate／probe | vcp 台帳裡的提交身分。candidate 有乾淨的 sealed 讀數，能參加 `submit final` 的選取；probe 只用來探排行榜，權重可能見過所有子集 |
| 登記 run | 不訓練的 run：把公開 notebook 用到的模型與檔案（名稱、版本、SHA）登記下來，讓含有它們的提交也有 run 卡可指 |
| slot | 平台上最終計分的名額，這場是 2 個 |
| P3 | 早期的提交系列：公開 notebook 的模型堆疊加上自有模型 |
| S1b、S1c' | 後期以公開 notebook 為基礎的兩發提交；S1c' 是 public 分數最高的一發 |
| v4～v9b | 自有模型融合提交的第 4 到第 9 版 |
| tier 3 | vcp 備份的最高層：權重也推到異地，並在異地逐檔驗證 |
| OOF | out-of-fold 預測：交叉驗證時每個樣本由沒見過它的那個 fold 預測 |

## 2. vcp 用到了什麼

### 2.1 版本時間線

| vcp | 期間（第一次到最後一次 attempt，UTC） | attempt 數 | 來源 |
|---|---|---|---|
| 0.1.0 開發版 | 09-07 到 09-08 | 14 | 浮動的 main checkout |
| 0.8.1 | 09-21 到 09-26 | 31 | 釘版 worktree：釘在 release tag 的獨立 checkout（從這裡起都是） |
| 0.10.0 | 09-26 到 09-29 | 15 | 09-25 發布、隔天升級 |
| 0.12.0 | 09-29 到 10-08 | 49 | 09-28／29 發布（tag 與 CHANGELOG 差一天）、09-29 升級 |
| 0.14.0 | 10-11 到 10-16 | 14 | 10-09 發布、當天升級 |

- 另有 1 次 attempt 在 0.8.0 的開發 build 上（09-21）。
- 跳過 0.9.x、0.11.0、0.13.0、0.15.0：升級時一次讀完中間幾版的升級說明。0.15.1（Kaggle CLI 警告的修正）在比賽結束後才發布。
- 一個 run 可以跨版本：某個 fold 的第 1 次 attempt 在 0.10.0、使用者要求暫停升級後，第 2 次 attempt 在 0.12.0 接續，兩份環境快照都留著。

## 3. 最終選取：紀錄鏈斷在最後一步

1. **事前規則**（2026-09-25 寫定，使用者選「事前寫死規則，手動勾選」）：
   - slot 1 = public 分數最高的一發；
   - slot 2 = 最好的「純自有模型」（每個權重都有 vcp run 卡），沒有就取第二高的 public；
   - 平手看 checkpoint 數，再看時間。
   - 10-11 經使用者同意修訂一次 slot 2 的條件；修訂只寫在 probe 日誌，沒有寫回規則檔。
2. **為什麼 `vcp submit final` 選不了**：
   - `final` 依 sealed（holdout）讀數挑 candidate 或 baseline，從不挑 probe。這是設計：probe 的權重見過所有子集，沒有乾淨的 sealed 讀數。
   - 這場 41 個 staged id 有 40 個是 probe，唯一的 candidate public 只有 0.865；holdout 也從沒解封。
   - 2026-09-26 的四次 `--dry-run` 都 FAIL `no_sealed_readings`，之後就沒再跑。
3. **計畫的兩發**：依規則是 S1c'（public 0.954）與 S1b（0.945），記在 10-15 的排名表文件裡。台帳沒有任何一列記「打算勾哪兩發」。
4. **實際勾的兩發**：P3 基線（public 0.943／private 0.927）與它的一個變體（0.941／0.926）。使用者說是自己勾錯。
5. **vcp 記到了什麼**：
   - 10-23 截止後的 `submit status`：`current=` 印出的正是計畫中的 slot 1（S1c'），但沒有欄位代表平台上的實際選取。
   - 唯一的紀錄是事後 `submit lock` 的理由文字：手寫了勾選的兩個 id。
   - 錯誤是人看 10-23 的排名表才發現的，不是 vcp 的檢查。
6. **代價**：S1c' private 0.938，比實際的 0.927 好約 750 名 Ⓤ；但 0.938 仍低於銅牌線 0.942 Ⓤ，獎牌結果不變。
7. **教訓**：
   - vcp 把「該送哪一發」記得很完整（run 卡、判決、stage、讀數），但「平台最後計哪兩發」在 vcp 之外，於是兩者不一致時沒有人提醒。
   - 修正排在 0.16.0（`docs/superpowers/plans/2026-10-23-rsna-wrapup-followups.md` §2；使用者 2026-10-30 的決定）：新的台帳事件記錄實際勾選（`submit select --record`）；截止前一段時間（預設 48 小時，可設定）還沒記錄、筆數和名額不同、或和 `final` 不同時，`submit status` 都 WARN。
   - Kaggle 的 SDK 有「只列已勾選」的查詢選項（伺服器是否照辦沒有驗證），CLI 2.2.5 沒有開放；vcp 只呼叫 CLI、不碰憑證，所以 0.16.0 只做手動記錄加提醒。

## 4. 三個事件

### 4.1 隱藏重跑出錯的提交（10-09，0.12.0）

- **症狀**：兩發 code submission 在隱藏測試集重跑時出錯，4.5 小時內就結束（完整重跑要 6.5–8 小時）。CLI 的列表顯示狀態 COMPLETE、兩個分數都是空的，沒有錯誤文字。
- **vcp 的反應**：`submit sync` 只寫有分數的列，兩發一直是 `unscored=2`，`submit status` 永遠 WARN；`final` 理論上可能選中沒有結果的 id。
- **影響**：兩發依規則判為無效（不是被拒），最終選取不受影響。
- **修正**：同一天找出原因、當晚發 0.14.0（VCP-048）：台帳新事件 `errored`，`sync`／`status` 的 `errored=`，`final` 跳過並記 `why=errored`。升級後第一次 sync 就把兩列補上。
- **限制**：錯誤訊息的文字 CLI 拿不到；vcp 不碰憑證，所以沒有。

### 4.2 訓練中磁碟滿（10-15，0.14.0）

- **症狀**：某個 fold 在第 4 個 epoch 結束、存續跑用的 resume 檔時失敗（`ios_base::badbit`），當時系統磁碟只剩 2.2 GB。VERDICT 是 `FAIL exit_code=1`，`reason=` 沒有提到磁碟。
- **殘留**：一個 266 MB 的 `.tmp` 留在 run 的輸出目錄；`train status` 不會列出它，到 10-30 還在。
- **影響**：損失一次 attempt（約 35 分鐘 GPU）。第 2 次 attempt 從第 3 個 epoch 的 resume 檔接續完成，紀錄完整。
- **後續**：隔天磁碟又只剩 4 GB。AI 代理先確認設定、run 卡、台帳與文件都沒有引用 8.9 GB 的重複上傳包與快取，把它們移到待刪資料夾，再由使用者親手刪除。
- **修正**：還沒有。排在 0.16.0（計畫 §3；門檻是使用者 2026-10-30 的決定）：`train run` 啟動前可用空間低於 10 GiB（預設，可覆寫）就 ABORT；磁碟滿時 `reason=` 寫明；`train status` 列出殘留的 `*.tmp`。安全清理工具 `vcp gc --dry-run` 排在課程結束（12/6）之後。

### 4.3 Kaggle CLI 的版本警告讓 `submit sync` 失敗（10-23，比賽結束後）

- **症狀**：截止後第一次 sync FAIL `platform_response: not JSON`。CLI 2.2.4 在伺服器版本較新時，把版本警告印在 stdout、JSON 前面。
- **影響**：private 分數一時同步不進台帳；發生在截止後約 17 小時，不影響任何決定。`submit.yaml` 的 CLI 是絕對路徑，無法在 PATH 上墊一層繞過。
- **處置**：把 CLI 升到 2.2.5，2 分 22 秒後 sync 成功，34 個 id 的 private 分數一次寫入，接著 `submit lock` 封住台帳。
- **修正**：0.15.1（10-24，PATCH）只略過答案前面的 `Warning:` 與空白行，經 redact 寫進 log；其他輸出仍然 FAIL。把警告浮到 VERDICT 與 `submit status`（WARN）排在 0.16.0。
- **沒驗證**：CLI 2.2.5 出錯列的 JSON 形狀是否和 2.2.4 相同（要用真的憑證呼叫一次）。

## 6. 有用的地方

1. **上傳回讀省下配額**（0.13.0 起）：10-11 平台以 HTTP 400 拒收三次，vcp 回報 `upload_failed:`、不寫列、不扣配額，換 id 後順利送出。
2. **id 長度守門**：一個超過 31 字元、會讓 sync 對不上的 id，在寫入台帳之前就被 `submit stage` 擋下。
3. **WARN 一路追到修正**：`unscored=2` 的 WARN 在 10-09 引出 VCP-048，當天修完發版。
4. **sealed 從頭到尾沒被碰過**：132 張收據 0 denied、0 讀過 sealed；最終選取是手動的，也沒有動到 holdout。
5. **事後稽核與逐位元重現**：09-25 查出兩個沒經過 vcp 的早期訓練，都用 `vcp train run` 重訓；其中 ConvNeXt fold 0 逐位元相同（350 個權重張量、OOF 檔 SHA 相同）。10-01 的稽核：當時 42 個 run 全部 `train status --verify` OK、`drift=0`。
6. **備份的假象被拆穿**：10-01 的紀錄顯示 42 個 run 的「備份」都只在同一台機器上；補傳到雲端、推清單、tier 3 驗過（`ok=154 missing=0 mismatch=0 drift=0`）。這正是 09-26 回報的 VCP-046 描述的情況（0.13.0 修正）。
7. **失敗沒有被藏起來**：9 次失敗、6 次中斷都留在 `train.yaml`，每次 attempt 的環境快照都在。

## 7. 沒用上、或還沒做到的

1. **選取路徑**：`final` 只有 `best_sealed` 一種規則，也不挑 probe。用 public 分數或外部權重決定最終提交的比賽，vcp 沒有支援的選取路徑（§3）。
2. **排行榜 probe 的預登記在 vcp 之外**：vcp 的預登記與判決只涵蓋 valA／valB 讀數。09-22 以後的 35 發上傳都是照事先寫好的文字規則決定，寫在 markdown 與 git 裡；vcp 沒有新的讀數、判決或預登記。
3. **dataset 改版功能沒用上**：每一版都是新的 dataset id，沒有用 `vcp data diff`；索引的 `changes` 一直是 0，`impact`／`stale` 也沒用過。
4. **多寫入者沒有實戰過**：兩條工作線各用自己的 configs root 與索引，靠「只有一條線寫台帳」的約定；共用台帳沒有啟用。
5. **收尾時的備份狀態**：最後一次 `backup status`（10-09）有 10 份清單未驗證，其中 2 份不完整（09-21 的 5-fold 清單只列了一個 fold）。09-26 已手動另建一份正確的新清單並驗過，但舊的兩份仍留在未驗證狀態。
6. **vcp 之外的工作**：OOF 量尺的比較、本機與 Kaggle 的一致性檢查、建立 Kaggle dataset 與 kernel。結果留在研究目錄與日誌，一致性數字只抄進 stage 的 `reason` 文字。

## 8. 對 1.0 的意義

- **0.16.0**（原排在 12/6 之後，使用者 2026-10-30 決定提前到 11 月上旬）：最終選取的紀錄與提醒（本文 §3）、磁碟滿的防護（§4.2）、CLI 警告的 WARN（§4.3）。
- **`vcp gc --dry-run`**（12/6 之後；11/13–12/6 框架凍結）：列出大檔與每個檔被誰引用，只列不刪（§4.2 的 8.9 GB 就是人工做的同一件事）。
- **Wave 1c**（1.0 前最後一塊）：程式碼快照與產物授權（稽核 VCP-004、006）。這場比賽的程式碼盤點曾兩次在 review 時才發現漏列的模組。
