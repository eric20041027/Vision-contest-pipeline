# vcp 命令參考

每一層的完整命令表、選項語意與範例流程。這份文件原本是 README 的主體，2026-09-15 開源整理時移到這裡，內容未刪改；README 現在只放概觀與 quickstart。

- 新手請先讀 [視覺導覽](../guides/VCP_VISUAL_GUIDE.md)。
- 每個命令的權威說明是 `uv run vcp <group> <command> --help`；本文與它不一致時以 `--help` 與程式碼為準。

## 資料層命令

| 命令 | 作用 | 主要選項 |
|---|---|---|
| `vcp data import` | 原始資料 → `dataset.yaml` + `samples.jsonl`；並寫一份 `source_audit`（逐列 sha 索引，VERDICT `source_audit=` `source_audit_state=`） | `--importer`、`--src`、`--name`、`--license`、`--url`、`--downloaded-at`、`--opt k=v`、`--raw-manifest full\|sizes` |
| `vcp data validate` | 重驗 card、samples 與 hash；產生或重用 `source_audit`（VERDICT `source_audit=` `source_audit_state=created\|reused`） | `--name` |
| `vcp data diff` | 比較兩個 immutable dataset version，只把 changed samples 發布為 verified `dataset_diff` artifact；no-op 為零事件 summary | `--from`、`--to`、`--id`、`--plugin`、`--policy` |
| `vcp data audit` | 座標 sanity、近重複與 test 重疊、來源檢查 | `--against`、`--max-bad-boxes`、`--min-box-px`、`--max-aspect`、`--max-cover`、`--hamming`、`--corr` |
| `vcp data split` | 固定多子集 plan（進 git、不可改） | `--plan-id`、`--subsets`、`--stratify-key`、`--group-key`、`--group-from-audit`、`--strategy` |
| `vcp data lineage` | 某訓練用了哪些子集 → 哪些驗證集還乾淨 | `--plan`、`--trained-on` |
| `vcp data export` | 子集 → COCO / YOLO 目錄 + manifest | `--plan`、`--subset`、`--format`、`--out`、`--opt view=`、`--opt copy=true`、`--unseal --reason`；每次匯出留一份 `access_receipt`（manifest 的 `receipt`、VERDICT `receipt=`）；VERDICT `identity=source_audit\|full_hash` |
| `vcp data labels` | 訓練標籤檔（`.csv` / `.jsonl`）對切分 plan 驗證後存成不可變的 `label_set/<id>`：每列的 id 依 `--id-field` 對到樣本；一個 id 一列；一張圖多列的標籤（偵測框）先依 id 併成一列（JSONL 放一個 list）；落在 `--subset` 以外的 dataset 樣本（驗證、sealed、未分配）→ FAIL `labels_outside_subsets:`（只報計數與前幾個 sample id）；不在 dataset 裡的列允許、記 `external=`；一列都沒對到 dataset 樣本 → WARN（多半是 `--id-field` / `--id-col` 選錯）；sealed 子集不能當 `--subset`（`labels_on_sealed:`）。同 id 同內容重跑 `reused=true`。VERDICT `rows=` `matched=` `external=` `subsets=` | `--name`、`--plan`、`--subset`（可重複）、`--file`、`--id-field sample_id\|view_path\|view_stem\|meta.<key>`、`--id-col`（預設 `id`）、`--id`、`--notes` |
| `vcp data materialize` | 每個 view 解碼一次成 npy / png 快取 + manifest | `--mode`、`--resize`、`--stack-seq`、`--window`、`--workers`、`--force`、`--decoder` |

每個命令以 `VERDICT cmd=... status=OK|WARN|FAIL|ABORT ...` 收尾；`--json` 時結果到 stdout、VERDICT 到 stderr。終端機的 code page 編不出的字元改印成 ASCII 跳脫（`--json` 則是 ASCII 跳脫的同一份 JSON），VERDICT 一定印得出來。eval / fuse / train / submit / backup 失敗時仍帶命令已知的 dataset / run / recipe / id 等識別欄位；深層錯誤可提供更精確的身分。

## Dataset evolution 與 provenance index

`vcp provenance rebuild|sync|ingest|impact|stale|explain|graph|status|verify-index` 從 canonical
dataset、plan、run、reading、artifact、fusion、submission 與 backup 建 deterministic graph。未指定
`--backend` 時仍使用 SQLite；每個 checkout 一份，檔案位於
`<data_root>/indexes/provenance-<configs root id>.sqlite3`（0.13.0 起；id 是 configs root 解析後路徑的 sha256 前
16 碼，跟台帳鎖檔同一個規則），可刪除、可由 canonical records 完整重建，不進 Git。PostgreSQL 是 optional、noncanonical 的另一個衍生索引；所有
命令可加 `--backend postgresql [--pg-service SERVICE]`，只有 `ingest` 另接受
`--strategy incremental|full|auto [--policy ID]`。`--policy` 只適用於 PostgreSQL auto（接受 v1
`postgres-adaptive-v1-…` 與 0.15.0 起的 v2 `postgres-adaptive-v2-…`）；auto 沒有
policy 時會 WARN 並安全選 FULL（已驗證的零 semantic work 除外）。

索引的 root（0.13.0，VCP-044）：索引記下它服務的 configs root 與 data root。每個 `vcp provenance` 命令都
解析 configs root（`impact`、`stale`、`explain`、`graph` 也是；`--configs-root`，預設 repo 的 `configs/` 或
`VCP_CONFIGS_ROOT`），VERDICT 帶 `root=<configs root id>`（失敗也帶）。SQLite 的索引檔名綁 configs root：
`--configs-root` 指到沒建過索引的 root、或 checkout 搬過 → `not_found:`；索引裡記的 root 跟命令的不同
（data root 換了路徑，或檔案被手動複製）→ 在任何前綴檢查之前 FAIL `root_mismatch:`（`index_root=<索引記的 id|none>`）；
同一個 root 內台帳被截短或改寫才是 `prefix_drift:`。0.12 以前的 `indexes/provenance.sqlite3` 不再讀（`not_found:` 會指出它；每
個 checkout `rebuild` 一次，沒有 0.12 使用者之後可刪）。PostgreSQL 一個 database 只服務一個 checkout：
`sync` 遇到別的 root 的 generation → `root_mismatch:`、不取代；`rebuild` 取代它並 WARN `replaced_root=`
（被取代那一代的 configs root id，所以只有 data root 不同的接手會跟 `root=` 同一個 id；人類訊息兩個路徑都印）；
0.13.0 以前建的 generation 沒記 root，`rebuild` 之前每個命令都 `root_mismatch:`。`status --json` 的 result
帶 `index`（這個 checkout 的索引在哪；PostgreSQL 時只是 `postgresql`）與索引記下的四個 root 鍵（`configs_root_id`、
`configs_root`、`data_root_id`、`data_root`；PostgreSQL 是 active generation 的）；`rebuild --json` 與
`sync --json` 的 result 帶 `replaced_roots`：PostgreSQL `rebuild` 取代別的 root 的 generation 時是那一代的四個
root 鍵（沒記 root 的舊 generation 是 `{}`），其他一律 null。

`vcp provenance graph --out FILE [--dataset D | --entity type:id] [--head D] [--detail overview|full]`
把索引畫成 Mermaid 圖（0.9.0 起）：副檔名決定格式——`.html`（瀏覽器直接開；Mermaid 11.17.2 從
jsDelivr 載入並以 SRI 驗證，需要網路）、`.md`（mermaid 區塊 + 圖例，GitHub 會渲染）、`.mmd`（純
Mermaid，可貼到 mermaid.live）。只讀索引、只寫 `--out`：`--out` 不能落在 data root 內，也只覆寫檔頭有
`generated by vcp provenance graph` 標記的舊圖，其他既有檔一律 FAIL（`exists:`、`out_in_data_root:`、
`out_not_absolute:`、`unsupported_format:`）；索引不存在時 FAIL 並提示先 `rebuild`。`overview`（預設）把 reading 摺進
run → judgement 的箭頭（箭頭標讀過的子集），收據 / export / 解碼快取 / source audit / diff / backup
不畫成節點（run 標 provenance 等級、有備份的節點加粗框、資料改版箭頭標 diff 與變更數），比賽自訂的
artifact kind 每種併成一個帶計數的節點；`full` 除 sample 外全部畫出。沒給 `--head` 時每個節點取「相對
各個現行 head 最差的狀態」，給了就只看相對該 head（語意同 `stale --head`）。範圍內有 BROKEN 或 REVIEW、
或 `.md` / `.mmd` 超過 Mermaid 預設上限（500 條邊 / 50,000 字元）時 WARN；VERDICT 帶 `out` `format`
`detail` `scope` `nodes` `edges` `folded` `broken` `stale` `review` `hash`（與 `rebuild` / `sync` 的
`hash` 同一個指紋），另視情況帶 `head`、`oversize=true`；`--json` 的 result 是摺好的節點與邊。

程式碼快照、trace 與授權（0.18.0）是一般的 artifact entity，彼此與 run、submission 之間的邊由既有的 `inputs` 路徑連出：快照 → trace、快照／授權 → 掛著它們的 run（經 run 的 `evidence` 清單）、授權的依據（產物依據的 `basis` input，或 run 依據的 `PRODUCED_BY {input: basis}`）、kernel 的快照 → submission 的 `CONSUMED_BY`。run entity 多一個屬性 `code_grade`（`traced` / `snapshot` / `commit`）：**等級是 `declared` 的 run 不寫這個鍵**（缺席 = `declared`，讀的人用 `.get("code_grade", "declared")`），所以沒有程式碼紀錄的圖位元組跟 0.17 相同。`code_grade` 是 run entity 的新屬性，`sync` 會當成既有 entity 被改寫而拒絕：升到 0.18.0 之後，每個 checkout 跑一次 `vcp provenance rebuild`（SQLite 與 PostgreSQL 都是）。圖的渲染沒有改，不畫程式碼等級。

`sync` 只接受新增 canonical records；既有 evidence 遭刪改、ledger prefix drift 或 diff
manifest/payload 不再符合會 fail closed。SQLite 操作與 status 語意見
[`DATASET_EVOLUTION_PROVENANCE.md`](../guides/DATASET_EVOLUTION_PROVENANCE.md)；PostgreSQL 的 optional
安裝、libpq service、全部 flags、repair、整合 harness 與 benchmark/calibration 命令見
[`POSTGRESQL_PROVENANCE.md`](../guides/POSTGRESQL_PROVENANCE.md)。目前 PostgreSQL live、large-scale、
calibration 與 held-out 結果仍待外部 runtime，不得把 offline tests 或 skips 當成資料庫通過。

## 量測層命令 `vcp eval`

| 命令 | 作用 | 主要選項 |
|---|---|---|
| `vcp eval ingest` | 框架輸出 → run 的標準預測檔（記 sha、建或更新 `run.yaml`） | `--run`、`--dataset`、`--plan`、`--subset`、`--format jsonl\|coco_results\|yolo_txt\|scores_csv`、`--src`、`--export-manifest`、`--trained-on`、`--framework`、`--notes`、`--weights PATH`、`--config PATH`、`--keep-input`、`--replace`、`--opt allow_unknown=true`、`--receipt ID`（可重複；把 `vcp train run` 之外產生的收據掛上 run）、`--evidence NAME=PATH`、`--labels ID`（皆可重複；參照記進 `run.yaml` 的 `evidence`，VERDICT `evidence=` `labels=`）、`--code LABEL=ID`（0.18.0，可重複；把一份 `vcp code snapshot` 寫的快照掛成 `code.<label>` 的 ref，binding `manual`；快照不存在 → `not_found:`、壞了 → `mismatch:`；VERDICT 一律帶 `code=`，沒有 `train.yaml` 的 run 有完好的快照 ref 就是 `snapshot`，否則 `declared`；已有 `train.yaml` 的 run 照記 ref，但等級仍由 `train.yaml` 算，不因它改變）；名稱 `authorization` 與以 `code.` / `code_trace.` 開頭的 `--evidence` 名稱保留（`role_reserved:`） |
| `vcp eval measure` | 護欄 → 每個乾淨 eval 子集 × 適用指標一列讀數；乾淨 = `trained_on ∪` 收據觀測到的子集都不含；`--subsets` 點到被讀過的子集 → `contaminated:` | `--run`、`--metrics`、`--subsets`、`--params k=v`、`--unseal --reason` |
| `vcp eval anchor` | 把既有讀數設成該 plan/子集/指標的護欄 | `--run`、`--subset`、`--metric`、`--params`、`--tolerance`（須有限且 ≥ 0）、`--replace` |
| `vcp eval sigma` | 估 σ_p 並 append | `--dataset`、`--plan`、`--metric`、`--method`（已登記的 σ_p 估法；內建 `splithalf` / `bootstrap` / `prior`，其餘以 `--plugin` 登記）、`--params`、`--subsets`、`--run`（bootstrap 預設取該 cell 的錨點 run）、`--prior --note`、`--resamples`、`--seed` |
| `vcp eval preregister` | 量候選之前先把主張寫死（進 git） | `--dataset`、`--id`、`--claim`、`--component`、`--class model\|tuning`、`--baseline-run`、`--candidate-run`、`--metric`、`--params`、`--subsets`、`--t-min`、`--min-bases`、`--sigma-method`、`--sigma-ratio` |
| `vcp eval judge` | 配對 bootstrap → Δ、se、t、基底數、σ_p 條件 → 判決；候選或基準讀過主張的子集 → `INVALID contaminated:<run>/<subset>`；判決記候選的 provenance | `--dataset`、`--prereg`、`--resamples`、`--seed`、`--strict`、`--unseal --reason` |
| `vcp eval status` | 孤兒預登記、run / 預登記 / 判決 / 錨點數、最新 σ_p；每個 run 另列 `labels=`（`dataset` 或 label_set id）與 `code=`（0.18.0，程式碼等級，`--json` 也有；VERDICT 不變；某個 run 的 provenance 讀不動時人看的行省略 `code=`，只有 `--json` 有） | `--dataset`、`--max-age-hours` |
| `vcp eval report` | 全部 run × subset 讀數（全精度）+ 每個判決的 last-vs-last | `--dataset`、`--metric`、`--plan` |

共用選項：`--json`、`--data-root`、`--configs-root`；前六個命令另有 `--plugin <module>`（可重複，import 該模組讓它登記指標、轉換器或 σ_p 估法），`status` / `report` 不碰登記表所以沒有。狀態與 exit code：未知 sample_id、缺讀數、選項不合法 → FAIL(1)；沒有錨點、σ_p 為 0、有孤兒預登記 → WARN(0)；護欄對不上 → ABORT(2) 且一列讀數都不寫，VERDICT 帶 `guardrail=FAIL anchor=<reading_id> got=<值>`。判決本身不是工具錯誤：`status=OK verdict=PASS|FAIL|INVALID`，要讓 FAIL 擋 CI 就加 `--strict`。

### 標準預測格式

`runs/<run_id>/predictions/<subset>.jsonl`，一列一個 sample，依 `sample_id` 排序、LF、UTF-8。payload 欄位由 task 決定，其餘為 null：

```json
{"sample_id": "s0001", "boxes": [{"x": 12.0, "y": 8.0, "w": 40.0, "h": 25.0, "category_id": 3, "score": 0.91, "view": 0}]}
{"sample_id": "s0002", "masks": [{"category_id": 1, "score": 0.88, "rle": "<COCO compressed RLE>", "meta": {"size": [512, 512]}}]}
{"sample_id": "s0003", "scores": {"cat": 0.7, "dog": 0.2, "bird": 0.1}}
{"sample_id": "s0004", "targets": {"age": 41.5}}
```

det → `boxes`、seg → `masks`（`rle` 與 `polygon` 恰一）、cls / multilabel → `scores`（鍵 = card 的類別名）、regression → `targets`。cls / multilabel / regression 每個 sample 都要有一列，缺列即 FAIL；det / seg 缺列視為零偵測，計入 `empty`。四種轉換器負責把框架輸出轉成這個格式，`yolo_txt` 與 `coco_results` 需要 `--export-manifest` 指向對應子集的 `vcp data export` 目錄。

### 一次判決的流程

```bash
uv run vcp eval ingest --run base --dataset D --plan fixed-v1 --subset valA --format yolo_txt \
  --src runs/base/valA --export-manifest exports/valA --trained-on train   # valB 同樣再跑一次
uv run vcp eval measure --run base
uv run vcp eval anchor --run base --subset valA --metric coco_map          # 之後每次 measure 都重驗
uv run vcp eval preregister --dataset D --id p1 --claim "新 backbone 更好" --component backbone-v2 \
  --class model --baseline-run base --candidate-run cand --metric coco_map # 先寫死，才准量候選
uv run vcp eval measure --run cand
uv run vcp eval judge --dataset D --prereg p1 --strict
```

`--class tuning` 的主張還要先有 σ_p（`vcp eval sigma --method splithalf|bootstrap|prior`），否則判決 `FAIL reason=no_sigma`。最後用 `vcp eval status --dataset D` 看有沒有寫了卻沒判的主張，`vcp eval report --dataset D` 看全部讀數與 last-vs-last。

比賽官方計分器、比賽專屬格式或自訂 σ_p 估法放在 `projects/<contest>/`，以 `--plugin projects.<contest>.metrics` 匯入，模組自己呼叫 `register_metric` / `register_converter` / `register_sigma_method` 登記，`src/vcp` 不出現比賽名稱。

## 融合層命令 `vcp fuse`

| 命令 | 作用 | 主要選項 |
|---|---|---|
| `vcp fuse recipe` | 驗成員後把配方寫進 git（`configs/datasets/<name>/fuse/<id>.yaml`，寫了不改） | `--dataset`、`--id`、`--plan`、`--method wbf\|mean\|rank_mean`、`--params k=v`、`--member RUN[:WEIGHT]`（可重複，順序有意義）、`--notes` |
| `vcp fuse build` | 成員預測檔 → 融合 run（`runs/fuse-<id>/`，`fuse.json` 記每個成員的 sha 與輸出 sha） | `--dataset`、`--recipe`、`--run`、`--subsets`、`--replace` |
| `vcp fuse ablate` | 每位成員一份「少了它」的變體配方與 run；`--preregister` 時每位成員一份準入預登記，交給 `vcp eval judge` | `--dataset`、`--recipe`、`--subsets`、`--no-build`、`--replace`（透傳給它觸發的每個 build）、`--preregister --metric M --metric-params k=v --bases valA,valB --t-min --min-bases` |

共用選項：`--json`、`--data-root`、`--configs-root`、`--plugin <module>`（自訂融合器以 `register_fuser` 登記）。融合結果就是普通 run：`trained_on` 取成員聯集、`source.framework=vcp.fuse`、`source.config_hash` = 配方檔 sha，量測與判決全用 `vcp eval`。同配方再 build 是 `cached=`；成員檔動一個位元是 FAIL `IntegrityError`；同一 run id 只綁一份配方。

### 一輪準入

```bash
uv run vcp fuse recipe --dataset D --id r1 --plan fixed-v1 --method wbf --params iou=0.6 --params min_score=0.02 --member a --member b:0.5
uv run vcp fuse ablate --dataset D --recipe r1 --preregister --metric coco_map   # 寫 r1-minus-*、建 fuse-r1 與 fuse-r1-minus-*、寫 r1-admit-*
uv run vcp eval measure --run fuse-r1 && uv run vcp eval measure --run fuse-r1-minus-a && uv run vcp eval measure --run fuse-r1-minus-b
uv run vcp eval judge --dataset D --prereg r1-admit-a    # PASS = a 證明了自己的位置；FAIL = 降權或移除，換新配方 id 再來
```

準入 = 「有它 vs 沒它」：候選是完整配方、基準是少了該成員的變體，主張 class 固定為 model。完整配方量測過就不能再寫準入預登記（`candidate_measured`），所以先 ablate 再 measure。成員重新 ingest 後直接 `vcp fuse ablate --replace`：這面旗子透傳給完整配方與每個變體的 build，沒變的子集照樣是 cached，舊 sha 進各 run 的 `history.jsonl`。

若 run 卡仍在但 `fuse.json` 遺失，快取命中或省略已宣告子集會 FAIL `not_found`；用 `vcp fuse build --replace` 恢復。此恢復會重建卡上全部子集（含 `--subsets` 未列者及位元相同者），先驗完所有成員才寫入，舊 sha 仍進 history。

`wbf`（boxes）：`iou`、`skip`（輸入框門檻）、`min_score`（融合後門檻）、`max_per_image`、`conf_type=avg|max`，語意同 ensemble-boxes 的 `weighted_boxes_fusion(allows_overflow=False)` 但在像素座標運算、依 (view, category) 分群、有尺寸才裁邊。`mean`（scores / targets）加權平均；`rank_mean`（scores）以子集為母體的名次平均，AUC 型指標用、不是機率。

## 訓練層命令 `vcp train`

| 命令 | 作用 | 主要選項 |
|---|---|---|
| `vcp train run` | 包在任何訓練命令外面：開始就寫 `run.yaml`（`trained_on` 由 export manifest 推導）、複製 config、環境快照、console 落檔、結束後登記 checkpoint 的 sha、上傳並驗證；子程序用 `MaterializedReader` / `Session.access` 留的收據結束時抄進 `run.yaml`（`receipts=` `denied=` `provenance=`），讀到 `trained_on` 以外的子集 → WARN `observed_beyond_trained_on=`。子程序的環境多了 `VCP_RUN_ID`、`VCP_DATA_ROOT`、`VCP_CONFIGS_ROOT`、`VCP_ATTEMPT`（第幾個 attempt）與有 `--seed` 時的 `VCP_SEED` | `--run`、`--dataset`、`--plan`、`--export DIR`（可重複）或 `--trained-on a,b`、`--venv DIR`、`--config`、`--seed`、`--framework`、`--cwd`、`--checkpoints GLOB`（可重複）、`--final GLOB`、`--upload DEST`（可重複）、`--resume`、`--notes`、`--evidence NAME=PATH`（可重複：子程序啟動前複製成 `evidence` 產物；結束時原檔變了 → WARN `evidence_changed=`）、`--labels ID`（可重複：`vcp data labels` 的標籤集，須與 run 的 dataset 版本、plan、`trained_on` 相容，否則 `labels_mismatch:`；同一名稱不能換角色或種類，第一次寫入前就 `evidence_conflict:`）；`--require-clean`（`--cwd` 所在 repo 的追蹤檔有改動 → 第一次寫入前 FAIL `dirty_tree:`，不在 repo 裡 → `not_found:`；未追蹤檔不擋）；VERDICT `evidence=` `labels=` `commit=`（前 12 位，不在 repo 裡是 `none`）`modified=` `untracked=`；追蹤檔有改動 → WARN，diff 存成 `train/git.<n>.patch`（10 MiB 以內）；patch 只有追蹤檔的差異，追蹤檔若含機密會跟著進 data root 與備份；結束時 HEAD 或追蹤檔的 diff 變了 → WARN `git_changed=`（取不到狀態時是 `git_changed=unavailable`）；`--min-free-gib G`（預設 `10`，單位 GiB；見表後的「磁碟空間」）；VERDICT 一律帶 `free_gib=`；`--code-root DIR`（可重複；0.18.0：另一個這次訓練用到的程式碼目錄，也要快照）、`--authorization ID`（0.18.0：第一次寫入前比對授權，見「程式碼快照、追蹤與授權」與 `vcp artifact authorize`）；VERDICT 一律帶 `code=` `code_snapshot=` `code_trace=`，有 git root 時帶 `untracked_code=`，條件欄位 `code_missing=` `code_gaps=` `code_changed=` `authorization=`；`--` 之後是訓練命令 |
| `vcp train upload` | 事後或換目的地上傳已登記的 checkpoint，冪等；遠端是 `<dest>/<run>/<名稱>`，run 內同名不同路徑的 checkpoint（多折的 `fold-k/model.pt`）取能分開它們的最少上層資料夾（`fold-0__model.pt`），只有資料夾也分不開才 FAIL `name_collision` | `--run`、`--dest`、`--only final` |
| `vcp train status` | attempts / checkpoints / 副本（唯讀；人類行印最後一個 attempt 的命令）；`backed=` / `unbacked=`（目前的 bytes 沒副本，會 WARN）/ `superseded=`（同路徑已被後來的登記取代、又從沒上傳過的舊 bytes，只報不 WARN——它們的副本再也不會出現）；VERDICT `evidence=` `labels=` `code=`（0.18.0，一律印：這個 run 最弱的 attempt 的程式碼等級；等級永不 WARN；人看的行每個 attempt 一行 `attempt <n>: code=<等級>`，`--json` 的 `code` 是 `{grade, attempts: [{n, grade, roots: [{label, snapshot, reason}]}]}`），`--verify` 另驗證據產物（壞了列成 `drift` 的 `evidence:<名稱>`；快照、trace、授權的 ref 也在裡面）；`tmp=`（一律印）：run 目錄（遞迴）、這個 run 每個已登記 checkpoint 所在目錄（不遞迴），以及 `--checkpoints` / `--final` 每個 glob 所在的目錄（不遞迴；`train run` 把 glob 原樣寫進 `started` 事件的 `checkpoints` / `final`，目錄是 `--cwd` 加 glob 第一個 `*`、`?`、`[` 之前的前綴的最近既存目錄，`**` 也不往下走；相對的 glob 以該 attempt 自己的 `--cwd` 為基準、不往 `--cwd` 之上走，`--cwd` 已不存在就略過）裡名稱以 `.tmp` 結尾（不分大小寫）的檔，例如 `torch.save` 寫不下留下的半個檔、vcp 自己的 `.<名>.<nonce>.tmp`；所以第一次存檔就失敗、從沒登記過 checkpoint 的目錄也看得到（0.16.0 以前的 vcp 跑的 run，`started` 事件沒有 glob，看不到）；事件檔讀不懂的行略過，不讓 `train status` ABORT；`tmp > 0` → WARN（attempt 還在 `running` 時也照列），人看的行 `tmp: <path> (<bytes> bytes)`，`--json` 的 `tmp` 是 `[{path, bytes}]`；唯讀、不刪 | `--run`、`--verify`（重算 sha） |

共用選項：`--json`、`--data-root`；`--configs-root` 只有 `vcp train run` 有（另外兩個命令只讀資料根目錄下的 run）。`--upload` 的目的地：`remote:path` 走 rclone，經 `vcp.backup.dest.RcloneDest`（`copyto --checksum` + `hashsum sha256` 逐檔比對，指令前綴 `vcp.backup.dest.RCLONE`；rclone 不在 PATH 又沒注入 runner 是 `VcpError("rclone_not_found: ...")` ABORT，指令有跑但失敗是 `PlatformError`〔FAIL，最後一行已去敏〕；`hashsum` exit 3/4 才算「還沒東西」，其餘非 0 或雜湊欄不是 sha256 都是錯誤），其餘是本機 / 掛載目錄（複製後讀回驗 sha）。訓練命令 exit ≠ 0 → `status=FAIL exit_code=N`，checkpoint 仍登記但不上傳；沒給 `--seed`、`--venv`、`--final` 各 WARN 一項。`run.yaml` 就是量測層的 run：之後 `vcp eval ingest --run R ...` 直接接上，不必再給 `--trained-on` / `--framework`。`--resume` 每次都新增一個 attempt，各記自己的 `command` / `seed` / `venv`；`train.yaml` 頂層那三欄刻意留著**第一個** attempt 的值（它描述 run 是怎麼開始的），要看最新的看 `attempts[-1]`。上一輪若還停在 `running`（vcp 自己崩過），`--resume` 會把它標成 `interrupted` 並在 `train.log.jsonl` 記一列 `note`。

磁碟空間（0.16.0；`vcp train run`）：
- **啟動前**：所有輸入檢查之後、第一次寫入之前，量三處所在的磁碟區——`runs/<run>/`（`run`）、`--cwd`（`cwd`）、每個 `--checkpoints` / `--final` glob 在第一個 `*`、`?`、`[` 之前的前綴（以 `--cwd` 為基準，`checkpoints`）；每個磁碟區量一次，取最小的可用空間。低於 `--min-free-gib`（GiB = 1024³ bytes，預設 `10`；不是有限數或 `< 0` → FAIL `invalid:`）→ ABORT `low_disk:`，VERDICT 帶 `free_gib=`（一位小數）`min_free_gib=` `disk_path=`，一個檔都不寫，`--resume` 也一樣（既有紀錄不動）。`--min-free-gib 0` 照量照記、永不 ABORT，也關掉下面失敗後的空間比較；磁碟區量不到 → WARN `disk_check=unavailable`，不 ABORT。跑完一個 attempt 的 VERDICT（OK、WARN、child 失敗的 FAIL）一律帶 `free_gib=`（量到的最小值；全部量不到是 `unknown`）；量測之後才以例外 FAIL 的（例如 `--final` 對到多個檔）沒有。量測結果寫進 `train/env.<n>.json` 的 `disk`（門檻、時戳、各磁碟區的 `path` `roles` `free_bytes` `total_bytes`）。`free` 是作業系統回報的磁碟區可用空間，**不反映 Windows 的使用者配額**。
- **child 失敗之後**（exit ≠ 0 且不是中斷；成功或中斷的不判）：再量同一組磁碟區，並讀 `console.<n>.log` 最後 64 KiB。有 `No space left on device`、`[Errno 28]`、`[WinError 112]`、`[WinError 39]`、`There is not enough space on the disk`、`Disk quota exceeded` 任一字樣（不分大小寫，依此順序）→ 狀態仍是 FAIL，`reason=disk_full: the command exited <n> and its console says "<字樣>"`、`disk_evidence=console`；否則最小可用空間低於 `--min-free-gib` → `reason=low_disk: … the disk may have filled`（只說可能：空間不足是事實，是不是失敗的原因 vcp 不知道；沒有 `disk_evidence=`）；都不是就沒有 `reason=`。有 `reason=` 時人看的行尾加 `; free space, then --resume`，`train.log.jsonl` 記一列 `note`（`key=disk_full|low_disk`、`marker`、`free_bytes`）。只說串流壞了的錯誤（C++ 的 `ios_base::badbit`、PyTorch 的 `file write failed`）、非 Python 程式的在地化訊息、64 KiB 之前的字樣、量測範圍以外的磁碟（`%TEMP%`、模型快取）都認不出，空間若已回到門檻以上也什麼都不報。
- **vcp 自己寫不下**：`train run` 第一次寫入之後，vcp 自己的紀錄（console、`train.yaml`、`run.yaml`、事件、環境快照，含 `--upload` 之後的 `uploaded` 事件與 `train.yaml`）遇到磁碟滿（`errno` ENOSPC / EDQUOT，或 Windows `winerror` 112 / 39）→ 停掉還在跑的 child，ABORT `disk_full:`、`disk_evidence=vcp`；清出空間後 `--resume`（還停在 `running` 的 attempt 會被標成 `interrupted`）。**只有 `vcp train run` 做這個轉換**：其他寫 yaml 的命令（`eval ingest`、`data import`、`submit init` 等）的 `OSError` 照舊成為 ABORT，`reason=` 是原本的例外文字。`--upload` 的目的地寫滿不算 vcp 的紀錄，仍是原本的 `OSError`。上傳步驟中途 `disk_full:` 時 attempt 已經結束，用冪等的 `vcp train upload --run R --dest DEST` 補，不是 `--resume`（VERDICT 的訊息也這樣說：`free space, then: vcp train upload --run <run> --dest <dest>`）。data root 所在的磁碟滿了，即使 checkpoint 寫在別顆磁碟，`train run` 也會停掉 child 並 ABORT：紀錄的完整優先於訓練的延續。
- **yaml 的原子替換**：`train.yaml`、`run.yaml`（與 `dataset.yaml`、`submit.yaml`）的整份重寫改成「同目錄暫存檔 → fsync → `os.replace`」，寫出的位元組不變；中斷或寫不下時目標檔仍是完整的舊版，目錄裡可能多一個 `.<名>.<nonce>.tmp`（`train status` 會列出）。Windows 上目標被別的程序開著（例如訓練中的 `train status` 正在讀、防毒或索引服務）時，`PermissionError` 最多重試 5 次、共約 1.55 秒，仍失敗就原樣丟出；POSIX 不重試。

### 程式碼快照、追蹤與授權（0.18.0；`vcp train run`）

`env.<n>.json` 的 `git` 只描述 `--cwd` 所在的 repo；0.18.0 讓每個 attempt 另外證明「跑的是哪些程式碼」。規則與快照本身見「程式碼快照命令 `vcp code`」，授權見「授權 `vcp artifact authorize`」。

- **順序**（所有輸入檢查之後、第一次寫入之前，被拒時一個檔都不寫）：(1) 環境探針（唯讀；從原本的第 6 步提前，失敗 → ABORT 而不是留下 `running` 的 attempt），多回報 `distributions` 與 `identity`；(2) `--venv` 裡裝了 vcp、而 `MAJOR.MINOR` 跟這個 vcp 不同 → FAIL `vcp_mismatch:`（`child_vcp=`；舊的 `Session` 讀不動新的 `train.yaml`，會到第一次登記 checkpoint 才當掉）；(3) 規劃 root；(4) 在記憶體裡掃描每個 root；(5) 給了 `--authorization` 才做的比對；(6) 0.16.0 的磁碟檢查（`low_disk:`）；(7) 在 `own_writes()` 裡為每個 root 寫或重用快照；(8) 既有的第一次寫入，`env.<n>.json` 帶 `code` `distributions` `identity` 三段，接著掛 `code.<label>` 與 `authorization` 的 ref（跟 `--evidence` 同一處）；之後子程序、結束時的比對。`--resume` 的每個 attempt 各做一次，`--authorization` 只對該次呼叫有效。
- **root 的規劃**：`cwd`（`--cwd` 所在 repo 的頂層，不在 git 裡就是 `--cwd`）、`script`（命令裡第一個存在、又不在其他 root 裡的 `.py` 所在的 repo 或目錄）、`editable`（探針回報 editable 的每個目錄，包括訓練 venv 裡的 vcp；label `dist-<名稱>`）、`extra`（`--code-root`，label `root-<n>`；不是目錄 → 第一次寫入前 FAIL `not_found:`）。同一個路徑只留第一個；巢狀的 root 把檔分給最內層。`--checkpoints` / `--final` 每個 glob 的基底目錄、生成程式碼登記表指到 root 內的位置不進快照，實際排除的目錄記在 `env.<n>.json` 的 `code.excluded_dirs`。
- **快照寫不成**：每個 root 持 `locks/code_snapshot-<id>.lock`（等 60 秒），已 commit 就重用，否則寫入。寫不成的四種，那個 root 的 `reason` 是：`locked`（等鎖逾時）、`partial`（同 id 的半途目錄已在，留到 `vcp artifact clean`）、`unwritable`（寫不進，例如路徑太長）、`drift`（複製時的 sha 跟掃描時不同）；掃描本身的 `too_large` / `unreadable` / `not_found`（探針回報 editable、但目錄已不存在）也一樣只標在那個 root。**沒給 `--authorization`**：那個 root 沒有快照，WARN，訓練照跑。**給了 `--authorization`**：fail closed——`drift` → FAIL `drift:`，`locked` / `partial` / `unwritable` → ABORT `code_unavailable:`（`code_root=<label>` `cause=`），run 的檔都沒寫，也不留一個沒有快照的授權 ref；授權沒有綁的 root（`--free`）失敗仍只 WARN，綁了的那個 root 失敗 → FAIL `unauthorized:`。
- **VERDICT 欄位**：

| 欄位 | 意思 | WARN |
|---|---|---|
| `code=` | 這個 run 的程式碼等級 `traced` / `snapshot` / `commit` / `declared`（最弱的 attempt；一律印） | 永不 |
| `code_snapshot=` | `ok`（每個 root 都有快照）／`partial`（有些沒有，`code_missing=<labels>`）／`none`（一個都沒有） | `partial`、`none` |
| `code_trace=` | `complete`／`incomplete`（`code_gaps=<outside+unlisted+changed>`）／`none`（沒有 trace，例如子程序沒用 `Session`；不 WARN） | `incomplete` |
| `untracked_code=` | 有 git root 時一律帶：各 git root 的「未追蹤但未被忽略的 `CODE` 檔」數加總（在快照裡，但沒有 commit 可以對照） | `> 0` |
| `code_changed=` | 結束時，快照 index 列過的檔有幾個不同或不見（只在 `> 0` 時帶）；`train.log.jsonl` 多一列 `note`（`key=code_changed`、`value=<n>`、`paths` ≤ 5 的 `<label>:<path>`、`roots`） | `> 0` |
| `authorization=` | 有給 `--authorization` 時 | |

  `untracked_code > 0` 時，子程序開始前 stderr 先印一行 `untracked_code=<n>: <前 5 個 <label>:<路徑>> (in the snapshot; git add or ignore them)`；要把它消掉就 `git add` 或加進 `.gitignore`（wandb 之類把程式碼存進沒被忽略的輸出目錄的工具，把那個目錄加進 `.gitignore`）。FAIL 的字：`vcp_mismatch:`、`unauthorized:`（`authorization=` `differs=<名稱>`）、`superseded:`（`authorization=`）、`drift:`（只在有授權時）、`not_found:`（`--code-root`）、`evidence_conflict:`（`code.<label>` 或 `authorization` 的 ref 名稱跟 `--evidence` / `--labels` 或舊 attempt 已有的 ref 撞名，第一次寫入前）；ABORT：`code_unavailable:`（只在有授權時）。`--evidence` 與 `Session.attach_evidence` 不能用保留的名稱（`authorization`、以 `code.` / `code_trace.` 開頭）→ `role_reserved:`。
- **程式碼等級**（讀取時由 `env.<n>.json`、`train.yaml` 與產物算出，不存；`train status`、`eval status`、`submit stage` / `final` 與 provenance 都讀它）：

| 等級 | 條件 |
|---|---|
| `traced` | 「快照齊全」（這個 attempt 的 `env.<n>.json` 有 root、每個 root 都有快照 id、run 的清單裡都有指向該 id 的完好 ref），加上這個 attempt 至少一份 `code_trace`、每份都 `complete` 且完好。`code_changed` 不影響它：trace 已對被 import 的檔做過比對 |
| `snapshot` | 快照齊全，而且沒有這個 attempt 的 `code_changed` note |
| `commit` | `env.<n>.json` 的 `git` 有 commit、沒有這個 attempt 的 `git_changed` note，而且：有 `status_sha256`（0.11 起）時 `modified == 0` 或有 `diff_sha256`，沒有時 `dirty` 為 false |
| `declared` | 其他（舊 run、沒有快照、讀不動的 `env.<n>.json`） |

  run 的等級 = 每個 attempt 的最低（resume 的權重來自每一個 attempt）；沒有 `train.yaml` 的 run（`eval ingest`）有完好的 `code.<label>` ref 就是 `snapshot`，否則 `declared`；fused run 取成員的最低。它跟 provenance 等級一樣會往下掉（快照或 trace 被刪、被改）。
- **import 追蹤**（`vcp.code.trace`）：在 `vcp train run` 底下（`VCP_RUN_ID` 對得上），程序第一次呼叫 `Session.current()`（`MaterializedReader` 也會）時登記一個 `atexit`，結束前把 `sys.modules` 每個有 `__file__` 的模組分類，寫成 `artifacts/code_trace/<run>-a<n>-t<seq>/`、掛 `code_trace.a<n>.<seq>` ref。分類（先對到的為準）：`generated`（生成程式碼登記表的位置，內建 `torch_inductor` `torch_extensions` `triton`；不雜湊、不算缺口，`register_generated(name, resolver)` 加一種框架）、`root`（在 index 裡、sha 相同）、`changed`（sha 不同或檔不見）、`unlisted`（在 root 底下卻不在 index：被忽略、之後才建、只有 `.pyc`）、`stdlib`（Windows 上含 `DLLs`；stdlib 與 site-packages 目錄重疊時取較深的那個）、`distribution`（site-packages）、`outside`（其他，含 zip 裡的模組與 HF 的 `trust_remote_code` 模組）。`complete` = `outside + unlisted + changed == 0`。不登記：`VCP_CODE_TRACE=0`、DataLoader worker（`multiprocessing.parent_process()` 不是 None）、`RANK` 有值且不是 `0`；fork 出來的程序不做。**永不改變結果**：整段包在 `try` 裡，失敗就不寫、stderr 印一行 `[vcp] code trace skipped: <原因>`，子程序的 exit code 不變。trace 的 `inputs` 是各 root 的 `snapshot.json`（名稱 `snapshot.<label>`），provenance 因此連得到快照。
- **只追得到 Python 模組**：不用 `Session` 的子程序、非 Python 程式、子程序再起的程序、DataLoader worker、非 0 rank、被 `os._exit` 或強制結束的程序都沒有 trace，等級最多 `snapshot`。就地編譯的擴充（`build_ext --inplace` 的 `.so` / `.pyd`）被 import 時是 `unlisted`，那個 attempt 到不了 `traced`。


### 收據與 provenance

訓練迴圈用 `with MaterializedReader(name, mode, plan_id=P, subset="train") as reader:`（或 `Session.current().access(subsets={"train"})`）讀資料：只有授權子集的列會被解析，關閉時存取器把它實際讀到的子集、ID 集合 sha、拒絕次數寫成 `artifacts/access_receipt/<run>-a<attempt>-<n>/receipt.json`——呼叫端只能加 `notes`。run 的等級由收據算出、不存：`receipt`（有 `purpose=train` 的有效收據）> `export`（無收據但從 `vcp data export` 目錄訓練）> `declared`（舊 run 或手填）；`vcp eval status` / `report`、`vcp submit status` 都印它。`submit.yaml` 的 `require_provenance: receipt|export|declared`（預設 `declared`）決定 `stage` / `final` 擋不擋候選；讀過 sealed 子集的候選一律 `observed_sealed:`。收據證明的是經 vcp 存取器的讀取；process 自己 `open()` 檔案不在證明範圍。

v0.6.0 起 `vcp data import` / `validate` 會留一份 `artifacts/source_audit/src-<dataset>-<hash16>/`（`audit.json` + 每列一個 sha 的 `index.jsonl`，內容定址、同內容重用）；存取器有它就不再整檔 hash `samples.jsonl`——未授權的列連讀都不讀、讀到的列先比 sha 再解析——收據記 `identity: source_audit`。舊資料集沒稽核照跑（`identity: full_hash`），但 `train run` / `measure` / `export` 會 WARN `source_audit=missing`，重跑 `vcp data validate` 就升級；稽核壞掉是 `mismatch:` FAIL，不退回。稽核產物本身壞掉（`vcp artifact verify --kind source_audit` 不過）時所有讀取都 `mismatch:` FAIL；把 `artifacts/source_audit/<id>/` 搬走再跑 `vcp data validate` 重建（內容定址，id 不變）。

自寫 PyTorch loop 只需要兩個名字：

```python
# torch 與 NAMES（你的類別名清單）是讀者自己的東西，vcp 不提供也不要求
from vcp.train import MaterializedReader, Session

with MaterializedReader("rsna-knee", "png-r256", plan_id="fixed-v1", subset="train") as reader:

    class Knee(torch.utils.data.Dataset):
        def __len__(self):
            return len(reader)

        def __getitem__(self, i):
            rec = reader[reader.ids[i]]  # rec.arrays: {"0": HxW(xC)} 或 {seq_id: SxHxW}
            x = torch.from_numpy(next(iter(rec.arrays.values())))
            y = torch.tensor([rec.labels.targets[n] for n in NAMES])
            return x, y

    s = Session.current()  # 在 vcp train run 底下才有
    s.register_checkpoint("ckpt/best.pt", final=True)
    s.note("val_auc", 0.91)
    per_attempt = f"evidence.a{s.attempt}.json"  # --resume 後遞增，與收據 id 的 -a<n>- 相同
    s.attach_evidence("teacher", "preds/teacher.jsonl")  # 讀過的檔：複製成 evidence 產物
    s.attach_labels("pseudo-v3")  # `vcp data labels` 驗過的標籤集
```

## 提交治理命令 `vcp submit`

| 命令 | 作用 | 主要選項 |
|---|---|---|
| `vcp submit init` | 寫 `configs/datasets/<test>/submit.yaml`（平台、配額與時區、截止、決選指標、輸出格式），並替 test dataset 建單子集 plan `all-v1`。`submit.yaml` 的 `selection_warn_hours`（0.16.0；數字 `>= 0` 或 `null`，預設 `48`）：`board_rule: best` 時，截止前幾小時起還沒有任何 `selected` 列，`status` 就 WARN `selection=missing`；`0` 表示從截止那一刻起，`null` 只關掉這一項（`slots`、`differs` 照常）。等於預設值時不寫出，所以 `init` 寫的檔舊 vcp 照讀；`init` 沒有對應選項，要改就在 git 裡改 `submit.yaml`，寫了之後舊 vcp 載入這份 profile 會 FAIL `extra_forbidden`，所有讀它的 vcp 都先升到 0.16.0；負數、`nan` 載入就 FAIL | `--dataset`（test dataset）、`--eval-dataset`、`--plan`、`--sealed`、`--platform manual\|kaggle`、`--competition`、`--kind file\|kernel`、`--board-rule last\|best`、`--quota N --day-tz TZ`、`--display-tz`、`--deadline`、`--metric`、`--writer`、`--writer-opt k=v`、`--kaggle-command` |

| `vcp submit upload` | Kaggle，一個交易（見表後）：再驗 sha → 把平台列表同步進台帳（同 `sync`，含綁定；讀不到 → FAIL `sync_failed:`、不上傳；`--no-sync` 略過 → WARN `sync=skipped`）→ 配額 → 重傳護欄（這個 id 已有任何 `uploaded` 列——vcp、手動或同步綁上的——→ FAIL `already_uploaded:`、VERDICT `uploads=`，訊息說要加 `--force "<理由>"`；`--force "<理由>"` 照傳，理由記進新列的 `reason`、VERDICT `forced=true`，空理由 → `invalid:`）→ `kaggle competitions submit` → `uploaded` 列。CLI 回 0 卻說 `Could not submit to competition` 是 FAIL `upload_failed:`、不寫列；CLI 非 0（例如等回應時斷線）也在同一個交易裡回讀：對上 → 照樣寫 `uploaded` 列（`confirmed=true`）並 WARN，VERDICT 帶 `exit_code=`；平台沒列出 → FAIL `upload_failed:`；判斷不了（`ambiguous` / `failed` / `interrupted` / 只對上已知的 ref）→ FAIL `upload_unconfirmed:`，兩者都不寫列、VERDICT 帶 `exit_code=`、`readback=`；印了 `Submission ref:` 或成功字樣即確認；都沒有（kernel 提交在 CLI 2.2.4 就是這樣）就回讀 submissions 列表：description 以這個 id 開頭、平台時間落在這次上傳前後 2 分鐘內的恰好一筆 → 確認並記下它的 `platform_ref`（回讀看過台帳已有的 ref——同 id 還列著的上一發——只認新的一筆；整個時間窗只看到已知的 → `known_ref`。列表呼叫——上傳前同步、`sync`、回讀——各有 120 秒逾時：同步逾時是 `sync_failed:`，回讀逾時是 `failed`；逾時結束整個程序樹——Windows 用 `taskkill /T /F` 結束，POSIX 讓子程序在新的 session 裡跑、用 `killpg` 結束——`uv tool` 之類的包裝程式也一併切斷）。VERDICT 帶 `confirmed=`、`platform_ref=`（有才帶）、`readback=matched\|not_listed\|ambiguous\|known_ref\|failed\|interrupted`（有回讀才帶）、`detail=`（平台回覆，redact 後截 160 字，也進 `logs/`）。`confirmed=false` 是 WARN：重傳之前先到平台看這個 id 在 `at` 前後有沒有一發——有就是上了，重傳會再吃一發配額；`submit sync` 之後會配對（它的 `unconfirmed=` 以 id 為單位，只對第一次上傳的 id 才代表沒上）。VERDICT 另帶 `ledger=`、`sync=ok\|skipped`、`bound=`（這次同步綁上的列數）、`cli_warnings=`（一律印：上傳前同步與回讀的列表呼叫裡，平台 CLI 印在答案前面的警告行，算不同的行數；`> 0` → WARN，每次都報；人看的行是每行一個 `cli_warning: <行>`，任一行含 `outdated`（不分大小寫）時多一行 `the platform CLI says it is outdated; upgrade the CLI that kaggle_command runs`；`--json` 只有 VERDICT 的數字，行本身看人看的輸出與 log）。同步寫進台帳的列（`foreign`、綁定、`scored`、`errored`）留著：之後的配額、重傳護欄或平台 FAIL 也在 VERDICT 帶 `sync=`、`bound=`、`cli_warnings=`（回讀後的平台 FAIL 帶到的是上傳前同步加回讀看過的行）。上傳前同步本身失敗（`sync_failed:`：列表讀不到、逾時、答案壞掉、配對寫入失敗）時，VERDICT 也帶 `cli_warnings=`（0.17.0；同步讀到的行加上例外帶的行，去重後算行數），但沒有 `sync=`、`bound=`：同步沒有完成，也沒有上傳。FAIL 只有個數，行在 log（每行一筆 WARNING `kaggle CLI: …`） | `--id`、`--message`、`--force "<理由>"`、`--no-sync` |
| `vcp submit record` | 手動平台：你在網頁上傳後回填，平台顯示時間換成 UTC；不讀平台列表；這個 id 已上傳過仍照記，WARN `already_uploaded=<n>`；`--platform-ref` 已經在某個 `uploaded` 列（例如 `sync` 綁上的）→ FAIL `exists:`、不寫列 | `--id`、`--at "YYYY-MM-DD HH:MM"`、`--tz platform\|utc`、`--platform-ref` |
| `vcp submit score` / `sync` | 回填 public / private；Kaggle 以 `competitions submissions` 回讀、配對、把別人的發記成 `foreign`（照數配額）。同一個 foreign ref 的狀態或分數變了（PENDING → COMPLETE 等）就多記一筆快照，VERDICT `refreshed=`；配額與到達仍每個 ref 算一次，其實是自己上傳的 foreign ref（`uploaded` 帶著它，或 `scored` 把它綁到某個 id、且與那個 id 的一發上傳相差不到 10 分鐘）不另計；配到的一發若這個 id 還沒有帶它 ref 的 `scored` 列，分數沒變也寫一列（同檔重傳才綁得上）；配到 id 卻沒有對應上傳的平台發（沒有帶同一個 ref 的 `uploaded` 列，這個 id 在平台時間前後 10 分鐘內也沒有不帶 ref 的上傳）補一列 `uploaded`（`source=platform`，PENDING 也補），算配額也擋重傳，VERDICT `bound=`；描述先配以 id 開頭的（`S2 same as S1` 是 S2 的），沒有才配提到 id 的；檔名＋時間的配對只看 vcp 與手動的上傳；同一個 ref 的 `uploaded` 列只算一次到達；同一個 ref 的分數與狀態沒變就不再寫 `scored`（重跑冪等；比的是這個 ref 最新的結果列，`scored` 或 `errored`），「最新分數」依平台時間 `at`。配到 id 的一發平台做完了卻沒有分數（Kaggle：狀態以 `.` 分割的最後一段轉小寫是 `error`，或是 `complete` 而 public 與 private 都空——CLI 2.2.4 把隱藏重跑出錯的 code submission 列成 `SubmissionStatus.COMPLETE`、兩個分數都是空字串，JSON 沒有錯誤訊息；帶分數的一律不算）→ 綁定照舊先做，再寫一列 `errored`（`source=platform`、平台的 `at`、`platform_ref`、`platform_status`，不帶分數），不寫 `scored`；這個 ref 最新的結果列（`scored` 或 `errored`）已經是狀態相同的 `errored` 就不再寫（重跑冪等）；之後平台替同一發補上分數，照樣寫 `scored`，以較新的那列為準；分數與沒分數之間來回時每一步都寫，結果跟平台最後的狀態一致。VERDICT 一律帶 `errored=`（這次寫入的列數），`errored > 0` 時 WARN（新的出錯只在寫入的那一次提醒），每寫一列印一行 `errored: <id> (…)`，`--json` 的 `errored` 是這些列的 id 清單；`upload` 的上傳前同步一樣會寫 `errored` 列，但 VERDICT 不加欄位。`sync` 的 VERDICT 一律帶 `cli_warnings=`（0.16.0；平台 CLI 印在列表答案前面的警告行——0.15.1 起解析會略過它們——算不同的行數，多頁同一行只算一次）：`> 0` → WARN，人看的行每行一個 `cli_warning: <行>`，`--json` 的 `cli_warnings` 是那些行（已 redact），任一行含 `outdated`（不分大小寫）時多一行 `the platform CLI says it is outdated; upgrade the CLI that kaggle_command runs`。警告只出現在這次命令的 VERDICT、輸出與 log，不寫台帳，每次讀列表各自報——CLI 沒升級，每一次 `sync` / `upload` 都 WARN；`status` 從不呼叫平台，所以不提示 CLI 過舊。失敗的 `sync` 也帶 `cli_warnings=<n>`（0.17.0）：從列表呼叫開始到配對寫入結束之間丟出的 vcp 錯誤都算——`sync_failed:`（逾時）、CLI 非 0（`exit_code=` 不被蓋掉）、翻頁超過上限、答案壞掉的 `platform_response:`（`not JSON`、缺鍵、分數或日期解析不了；壞的那一頁的警告行與前面頁的都算）、配對時讀 `stage.json` 失敗；`n` 是錯誤帶的行加上列表已經讀回的行，去重。`kaggle_not_found:`（ABORT，在任何 CLI 呼叫之前）是 `cli_warnings=0`；這個範圍之前的失敗（`manual_platform:`、`locked:`、`not_adopted:`、profile 或台帳讀不動）與本機寫不下的 `OSError`（ABORT）沒有這個欄位。FAIL 時只有個數：失敗的 VERDICT 不印人看的行，也不印升級提示，行在 log。用 `register_platform` 登記、`list_submissions` 仍回傳 list 的平台照常運作（`cli_warnings=0`）；`list_submissions` 與 `parse_submissions` 的回傳型別在 0.16.0 改了，直接呼叫它們的程式要改（`PlatformList`） | `--public`、`--private` |
| `vcp submit final` | 已準入且已上傳的候選依 sealed 讀數（同分看 public、再看 staged 時間）選出 `final_slots` 個，寫決選表並封槍。candidate 與 baseline 最新一發的結果是 `errored`（平台做完卻沒有分數）→ 不排名，表裡 `why=errored`，列在沒排名的清單裡（WARN）；判斷順序是 `probe`、`not_uploaded`、`errored`，然後才是 sealed 讀數與來源檢查；重傳之後出分就照常排名。`board_rule=last` 而最後一發不是選中的 → WARN `needs_reupload=`，並印出重傳的命令：Kaggle 是 `vcp submit upload --dataset T --id <選中> --force "final re-send"`（選中的 id 不受封槍擋，但它上傳過，要 `--force`）；手動平台是網頁重傳後 `record`。`board_rule=best`（平台有決選勾選）時另核對 `select --record` 記下的選取（0.16.0；排名與 `final` 列一個位元組都不變，決選只看 sealed 讀數）：已有 `selected` 列、而集合跟這次的 `chosen` 不同 → WARN，VERDICT 帶 `selection=differs`，人看的行印兩邊（沒有 `selected` 列或相同時不帶這個欄位；0.17.0 起比的是標籤，`S3@123` 就是 `S3`，被台帳認成自己上傳的 `foreign:<ref>` 就是那個 id；已記的是空選取〔`select --none`〕也是 `selection=differs`，人看的行改印 `selection: final chose <ids>; nothing ticked (recorded <時戳>): the platform picks by its own rule`）；一律多印一行 `next: select <chosen> on the platform, then: vcp submit select --dataset T --record <chosen>`（`--dry-run` 也印）。`board_rule=last` 沒有這兩項（它照舊靠 `needs_reupload=`）。`--slots` 覆寫的名額會寫進 `final` 列的 `slots`，之後 `select` / `status` 算「應該勾幾個」取最新 `final` 列的 `slots`，沒有 `final` 列才用 `final_slots`。0.18.0 起 `require_code` 不是 `declared` 時，`final` 重讀每個 candidate 的程式碼等級（跟 `stage` 同一套讀法；kernel 提交另看 `--code` 的快照還成不成立），不夠的在表裡 `why=code_required`（排在 `provenance_required` 之後），列在沒排名的清單裡；`final` 列的形狀不變 | `--slots`、`--dry-run` |
| `vcp submit select` | 記下你在平台上實際勾選的最終提交（0.16.0 起；vcp 不替你勾，也從不呼叫平台，Kaggle 與手動平台一樣）。`--record` 與 `--none` 恰好給一個。`--record` 是逗號清單，每一項是一個「條目」：`<id>`（這個 id 的某一發，0.16.0 的寫法）；`<id>@<platform ref>`（0.17.0；這個 id 在平台上的那一發，以第一個 `@` 切開、兩側去空白，用在同一個 id 傳過兩次〔`--force` 重傳、`final` 的 re-send〕而你要說是哪一發時）；`foreign:<platform_ref>`（隊友或網頁上傳的一發，標籤格式同 `status` 的 `current`；先判斷前綴，所以 ref 可以含 `@`）。`--none`（0.17.0）記「平台上一發都沒勾」，寫一列 `chosen: []`，平台照自己的規則決定（Kaggle 這時自動用 public 最好的兩發；vcp 不模擬、也沒有驗證）。整段在台帳交易裡，檢查全做完才寫，任一項不過就 FAIL、一列都不寫；檢查在拿到鎖、讀完台帳之後，所以鎖被佔時連壞輸入也是 ABORT `locked:`。順序：(1) `invalid:`——`--record` 與 `--none` 都給或都沒給、`--record` 去空白後沒有任何項、同一項兩次、`@` 的一側是空的、同一個 id 同時以 `<id>` 與 `<id>@…` 出現、同一個 ref 被兩項指到（`S3@123,foreign:123`）；(2) 依輸入順序逐項：`foreign:<ref>` 的 ref 不在台帳的 `foreign` 列 → `not_found:`（ref 其實是某個 id 的上傳時，訊息加一句要記成 `<id>@<ref>`）；`<id>`、`<id>@<ref>` 沒有 `staged` 列 → `not_staged:`、沒有任何 `uploaded` 列 → `not_uploaded:`；`<id>@<ref>` 的 ref 不是這個 id 的上傳（看這個 id 的 `uploaded`、`scored`、`errored` 列帶的 `platform_ref`；未確認的 vcp 上傳要等 `sync` 對上才有 ref）→ `not_found:`，ref 是別的 id 的就說是誰的。`not_staged:` `not_uploaded:` `not_found:` 帶 `id=`（那一項）。最新一列 `selected` 的條目集合（以字面比、不管順序）跟這次相同 → 不寫、`written=false`，`--message` 只在寫列時用、不改舊列；`S3` 改記成 `S3@123` 字面不同，是更精確的紀錄，會寫新列；`--none` 而最新一列已經是空的 → 不寫。否則 append 一列 `selected`（`source=manual`、`chosen` 照輸入順序）。台帳記的是人說的，讀取時才解析：ref 的歸屬會在之後的 `sync` 改變，所以 `foreign:<ref>` 之後被台帳認成自己的上傳時，台帳仍寫 `foreign:<ref>`，`select` 自己、`status`、`report`、`final` 讀到時把它當成那個 id；`select` 對這種條目多印一行 `note: foreign:<ref> is <id>'s upload; `bad ledger row`——每個 submit 寫入命令、`status`、`report`，以及讀台帳的 `backup manifest`、`backup verify`。跟 `errored` 不同，`selected` 只由人下的命令寫，所以在第一次 `select --record` 之前 0.15 與 0.16 可以共用台帳；誰先記選取，誰負責先讓每個讀寫那份台帳的 `--none`，誰負責先讓大家升級（在那之前 0.16 與 0.17 可以共用台帳，這一列只由人下的命令寫）。`<id>@<ref>` 條目 0.16.0 照常載入（`chosen` 仍是非空、不重複的字串 list），但讀錯：`status` / `select` / `final` 可能誤報 `differs`，條目數與標籤數不同時誤報 `slots`，`report` 不標那些列——多半只會多 WARN、不會 FAIL，建議升級但不擋；例外：沒有 `final` 列、可選的 id 有兩個以上、記了 `A@1,A@2` 時，0.17.0 報 `slots`（不同標籤數 1 ≠ 預期 2），0.16.0 照條目數 2 報 `ok`，這一種舊版反而少 WARN。`foreign:<ref>` 的解析只改讀法，台帳不變。

寫到一半就當掉的寫入者，會留下沒有換行的最後一列：唯讀命令略過它；寫入者在鎖內嚴格讀，殘列解析不了就 FAIL `bad ledger row`。處理：先確定沒有 vcp 寫入者在跑，刪掉那個殘列（它從沒被當成一列讀過）；有 provenance 索引就再跑 `vcp provenance rebuild`（檢查點可能記了殘列的位元組，截掉之後 `sync` 會 `prefix_drift:`）。`ledger: shared` 時，一個 checkout 跑 `vcp provenance rebuild` / `sync` 碰上別的 checkout 正在寫正本，可能 FAIL `canonical_drift: inputs changed …`；重跑即可。

程式碼等級的門檻（0.18.0）：`submit.yaml` 的 `require_code: declared | commit | snapshot | traced`（由弱到強，等級的定義見 `vcp train run` 後的「程式碼快照、追蹤與授權」）決定 `stage` / `final` 擋不擋候選；預設 `declared`，等於預設時不寫出（`init` 沒有對應選項，要改就在 git 裡改 `submit.yaml`；寫了之後舊 vcp 載入這份 profile 會 FAIL `extra_forbidden`，所以讀它的 vcp 都先升到 0.18.0）。只有 candidate 會被擋：baseline 與 probe 對每個低於要求的 run 寫 pairing check `code:<run>=<等級>`，不 FAIL。`stage.json` 的 `code` 與 `Artifact.code_snapshot` 只在有值時寫出，舊 vcp 讀到會 FAIL。

候選 = (eval 側 run, test 側 run) 一對：單模比 `weights_hash`（用 `vcp eval ingest --weights PATH` 給 run 身分），融合比 method / params / 成員權重並逐成員遞迴。`candidate` 需要 `vcp eval judge` 的 PASS 判決（融合 run 每個成員各一份）；`baseline` / `probe` 要 `--reason`，probe 永不進決選。沒有 `--override`。vcp 不碰 Kaggle 憑證：只呼叫 kaggle CLI，輸出經 redact 才落地。

### 一次提交

```bash
uv run vcp eval ingest --run good.test --dataset D-test --plan all-v1 --subset test --format scores_csv --src preds.csv --weights runs-ultra/good/weights/best.pt
uv run vcp submit stage --dataset D-test --id SUB34 --eval-run good --test-run good.test
uv run vcp submit upload --dataset D-test --id SUB34            # 手動平台改 record --at "2026-08-31 21:28"
uv run vcp submit sync --dataset D-test                          # 手動平台改 score --public 0.7916
uv run vcp eval measure --run good --subsets holdout --unseal --reason "final pick"
uv run vcp submit final --dataset D-test                        # 自動封槍；needs_reupload 時照印出的命令重傳（--force "final re-send"）
uv run vcp submit select --dataset D-test --record SUB34         # 在平台上勾好之後記下來（board_rule: best）；status 沒有 selection= 的 WARN 才算對上
# 同一個 id 傳過兩次、要指明勾的是哪一發：uv run vcp submit select --dataset D-test --record SUB34@<平台 ref>（ref 看 upload 的 platform_ref=）
# 刻意不勾：uv run vcp submit select --dataset D-test --none
```

|---|---|---|
| `vcp backup manifest` | 從結論反向走證據圖，寫 `configs/datasets/<name>/backup/<id>.json`（進 git、寫一次不改）：每個檔的角色、tier、sha、大小、服務的結論；checkpoint 以路徑為身分（每個路徑最新一筆），同名不同路徑的都會進清單；同一路徑有多個驗過的上傳時優先選 rclone 的。VERDICT 帶 `local_copies=`（只在這台機器上的副本數，只供參考）。建完自檢：清單漏了 run 紀錄登記的檔 → ABORT `manifest_incomplete:`（建清單程式的 bug，什麼都不寫） | `--dataset`、`--conclusion submission:<id>\|judgement:<prereg>\|run:<id>\|all`、`--id` |
| `vcp backup push` | 先小後大推到 rclone 遠端或本機目錄（`<dest>/data\|configs\|external/…`），只推目的地沒有或不同的檔，推完逐檔比對 sha；`train upload` 驗過的權重副本（`remote_copy`）在 rclone 遠端上、或就在目的地裡的不重推，其他（只在這台機器上的）跟著 `--tier 3` 當一般檔推到目的地：來源先用原 checkpoint，sha 不符再用 `train upload` 那份，都不符 → 動任何檔之前 FAIL `drift:` / `not_found:`；VERDICT `local_copies=`。`--tier 3` 先查清單完整性：缺 run 紀錄登記的檔 → FAIL `manifest_incomplete:`（`incomplete=`），不動任何檔、不寫列 | `--manifest`、`--dest`、`--tier 1\|2\|3`（累積到 N；預設 1）、`--forget-remote`（整份清單的每個檔——含更高 tier 與只在這台機器上的副本——都在目的地驗過才 `rclone config delete <remote>`；清單缺檔 → `forget_refused:`、`incomplete=`） |
| `vcp backup verify` | 三層稽核：副本（給 `--dest` 才做；`absent=` 是清單時已缺、目的地也沒有，不算失敗）、本機一致性（卡 ↔ 預測檔、`train.yaml` ↔ checkpoint、`fuse.json` ↔ 成員、`stage.json` ↔ 候選檔、台帳 ↔ `stage.json`、清單 ↔ 現在的檔）、時戳（台帳逐列 `ts` 可解析且單調、卡的 `*_at` 可解析）。副本層對沒被目的地 cover 的 `remote_copy` 在目的地查（不在就是 `missing`，不看 `present`），VERDICT `local_copies=`；一致性層另查完整性：清單的 `run.yaml` / `train.yaml` 在清單建立前登記的每個 checkpoint 路徑與掛上的證據都要在清單裡（任何角色都算）→ 缺的是 `manifest_incomplete`（`reason=` 第一順位，補救是換新清單），VERDICT 一律帶 `incomplete=` | `--manifest`、`--dest`、`--tier`（副本層只查 tier 1..N，預設 3 = 全部） |
| `vcp backup pull` | 從目的地把清單裡的檔拉回原相對路徑、讀回驗 sha；本機已有且不同 → `conflict`，`--overwrite` 才蓋（舊檔留 `.bak-<時戳>`，新檔驗過才留）；`external_skipped=` 是清單外的絕對路徑，只在目錄已存在時還原；被目的地 cover 的 `remote_copy` 從它自己的位置拉，其他的先從目的地拉、目的地沒有再退回 `train upload` 留在本機的那份 | `--manifest`、`--dest`、`--tier`（預設 3）、`--overwrite` |
| `vcp backup status` | 每份清單最新的 push / verify、從未推過的 tier、`rclone_conf=present\|absent\|unknown`（唯讀）；`verified` 要有一次 verify 連 tier 3 副本層都過，只驗本機兩層記 `local_ok`；每份清單都重算完整性：缺檔 → `verified=false`、WARN，VERDICT `incomplete=<缺檔的清單數>`（本機沒有 run 紀錄時看 verify 列的 `incomplete`，再看清單的 `vcp_version`：0.10.0 以前 → `unchecked`）；清單列出的 run 紀錄讀不了也是 `unchecked`，備註寫出那個檔與原因，其他清單照常列出（`backup verify` 照樣 FAIL）；每份 `unchecked` 的原因都寫在備註裡；清單有沒被目的地 cover 的本機副本時，只有帶 `local_copies` 的 verify 列與 tier 3 push 列（0.13.0 起寫）算數 | |

tier 1 決策層（台帳、卡、判決、預登記、配方、快照、候選檔；KB 級）、tier 2 重現層（預測檔、樣本、`train/`、logs；MB 級）、tier 3 權重層（GB 級，只在要求時）。0.18.0 起四個新 role：`code_snapshot`（tier 2：run 清單掛的程式碼快照，以及 kernel 提交的 `Artifact.code_snapshot`）、`code_trace`（tier 1）、`authorization`（tier 1）、`authorization_basis`（tier 2：產物依據的 `manifest.json` 與檔案，帶授權當時釘住的 sha；run 依據當一般 run 走證據圖，`run.yaml` 不見 → `not_found:`，`all` 與 `gc scan` 的單位則略過並 WARN）。備份記的是證據「現在的樣子」：依據被改寫而仍在時照記，`consume` 之後會判它 `superseded:`。快照內可能有寫死的機密，會跟著進清單與異地備份。`cache/`、`raw/` 永不進清單。清單只含路徑、sha、大小、時間與 dest 字串；vcp 不讀 rclone 設定檔內容，rclone 的輸出經 redact 才落地，台帳 `backup.log.jsonl` 只增。台帳在清單之後長大：verify 不算漂移，push 推的是清單那一刻的快照（前 N 位元組），pull 視為已有；被改或截短才算漂移。0.10.0 以前、為「同檔名不同路徑」的多折 run 建的清單，0.13.0 起會報 `manifest_incomplete:`：用新 id 重建清單，重推、重驗（舊清單留著當歷史）。

### 機器回收前的撤離順序

```bash
uv run vcp backup manifest --dataset D-test --conclusion submission:SUB34 --id sub34   # 最終發需要的一切
uv run vcp backup push --dataset D-test --manifest sub34 --dest gdrive:vcp/backup --tier 1   # 先救決策層
uv run vcp backup push --dataset D-test --manifest sub34 --dest gdrive:vcp/backup --tier 2   # 再救重現層
uv run vcp backup manifest --dataset D --conclusion all --id all-final                        # 有空再救全部
uv run vcp backup push --dataset D --manifest all-final --dest gdrive:vcp/backup --tier 3 --forget-remote
uv run vcp backup status --dataset D-test                                                    # rclone_conf=absent 才走
```

### 賽後重建

```bash
git pull                                                                # 清單與台帳跟著 configs/ 回來
uv run vcp backup pull --dataset D-test --manifest sub34 --dest gdrive:vcp/backup --tier 2
uv run vcp backup verify --dataset D-test --manifest sub34 --dest gdrive:vcp/backup --tier 2
uv run vcp submit verify --dataset D-test --id SUB34                    # 位元級重現候選檔
```

## 磁碟盤點命令 `vcp gc`

| 命令 | 作用 | 主要選項 |
|---|---|---|
| `vcp gc scan` | 0.17.0 起。列出 data root、檢查點目錄與 `--root` 底下的大項目，每一項的類別與誰引用它，再寫一份不可變的稽核產物 `gc_scan`。**只列不刪**：沒有 `--apply`、`--delete`，以後也不會加；不改任何既有檔、不上鎖（台帳以唯讀方式讀，略過寫到一半的最後一列）、不暫停訓練，結果是掃描當下的快照。每次掃描一個新產物，同樣不做 supersedes | `--root DIR`（可重複）、`--min-mib M`（預設 `100`）、`--no-record`、`--json`、`--data-root`、`--configs-root` |

共用選項：`--json`（結果到 stdout、VERDICT 到 stderr）、`--data-root`、`--configs-root`。

為什麼是 `gc scan`，不是 RSNA 收尾後記寫的 `vcp gc --dry-run`：一個永遠必填的旗標暗示有一天會有不帶它的刪除模式，而 vcp 不刪任何東西；名字本身就說它只看。既有的 `vcp artifact clean --apply` 範圍不變（只移除超過寬限期的半途目錄與 `.tmp`）。

```bash
uv run vcp gc scan --root projects/D            # 專案目錄不在 data root 裡，要自己用 --root 加
# 讀 unreferenced / debris / duplicate of …，確認沒有筆記、notebook 或別的工具需要之後，由人自己刪
uv run vcp artifact verify --kind gc_scan --id <VERDICT 的 scan=>   # 掃描的 id 就是「當時沒有引用」的證據
```

### 選項

- `--root DIR`（可重複）：另外遞迴掃的目錄；不存在或不是目錄 → FAIL `not_found:`。
- `--min-mib M`：列出的項目門檻（MiB = 1024² bytes），預設 `100`；不是有限數或 `< 0` → FAIL `invalid:`；`0` 列出每個項目。門檻只決定列出哪些項目，各類別的總量一律算全部。
- `--no-record`：不寫 `gc_scan` 產物，VERDICT `scan=none`。用在不能寫的 data root（唯讀快照、別人的機器）。每個命令共用的每日 log 照寫（`run_command` 在命令本體之前就建 `logs/`、寫 VERDICT），所以真正唯讀的 data root 上 log 寫不了就跟其他命令一樣。
- 沒有 `--dataset`：永遠讀整個 data root 與這個 configs root 的全部引用，因為只讀一部分的引用，會把別的 dataset 用的檔說成沒被引用。打錯的 `--data-root` 不另外檢查，掃出來只有 `logs/`，一眼看得出來；找不到 configs root 是既有的錯誤。

### 掃哪裡

1. **data root**，遞迴。
2. **檢查點目錄**，不遞迴：每個有 `train.yaml` 的 run，其已登記 checkpoint 所在的目錄，加上 `started` 事件裡 `--checkpoints` / `--final` glob 所在的目錄（規則與 `train status` 找 `.tmp` 的相同，兩者共用 `vcp.train.status.checkpoint_dirs`）。未登記的中間 checkpoint、半途的 `.tmp` 通常就在這裡。已不存在的目錄與磁碟根不掃。
3. **`--root`**，遞迴。

規則跟著路徑走，不跟著根走：data root 底下的檔一律套 data root 的分類與單位，即使是從 `--root ~` 走進來的（走 `--root` 遇到 data root 就不往下走，data root 自己是一個根）；檢查點目錄直接底下的檔一律逐檔為單位；其餘 `--root` 底下的檔才以「根的直接子項」為單位。每個檔只算一次（以 `resolve()` 後的路徑去重），被別的根包住的 `--root` 仍列在 `scan.json` 的 `roots`。不跟隨符號連結與 junction（不往下走、也不計大小）；讀不了的目錄（`PermissionError` 等 `OSError`）記進 `unreadable`、跳過、不 ABORT。依目錄彙總，不把每個檔留在記憶體（`raw/` 可能有幾十萬個檔）。預設不掃各 run 的 `--cwd`：那常是整個 repo 加 venv，要看就用 `--root`。

### 引用來源（只讀正本）

| 來源 | 被引用的路徑 | 引用者 |
|---|---|---|
| data root 每個 `runs/<id>/run.yaml`（不論屬於哪個 dataset） | backup 的 `Collector.walk_run` 列的每個檔：run 卡、預測、`history.jsonl`、`fuse.json` 與配方、`train.yaml`、`train.log.jsonl`、`train/`、每個 checkpoint（含 `train upload` 驗過的副本）、收據、source audit、證據與標籤集產物 | `run:<id>` |
| 同一個 run 的 `train.yaml` | `exports[].dir`、`kind: local` 的 `uploads`（`<dest>/<run>/<名稱>`）、`venv` 與每個 attempt 的 `venv`、`config.path` | `run:<id>` |
| 這個 configs root 的每個 dataset | `dataset.yaml`、plan、unseal 紀錄、量測台帳、`samples.jsonl`、`raw_manifest.txt`；每個預登記；每個 staged submission 的 `stage.json`、上傳檔與台帳，以及它們走到的 run；`dataset.yaml` 的 `image_root`（目錄） | `dataset:<name>`、`judgement:<name>/<prereg>`、`submission:<name>/<id>` |
| 每份 backup 清單 | 每個 `FileEntry` 的本機路徑 | `backup:<name>/<manifest>` |
| `backup.log.jsonl` 的 `push` 列 | `dest_kind == "local"` 的目的地整棵 | `backup:<name>/<manifest>` |
| data root 每個有 `manifest.json` 的產物 | `spec.inputs[].path` | `artifact:<kind>/<id>` |

走法就是 backup 的證據走法（`vcp.backup.evidence.Collector`）換上一個不雜湊的記錄端，所以兩邊的引用不會分叉；backup 清單的位元組不變。引用者字串是 `<結論>#<role>`，例如 `run:r7#checkpoint_final`、`submission:t/S3#artifact`；目錄引用（export、venv、`image_root`、本機 backup 目的地）涵蓋底下每個檔；路徑一律 `resolve()`、在 Windows 上 `normcase` 之後比對。configs root 沒有 card 的 run（別的 checkout 或別的專案共用這個 data root）仍以 `walk_run` 走過，所以它的 checkpoint 不會被說成沒有引用。

**不讀 provenance 索引。** 它是衍生、可刪、可能過期或不存在的索引，記的是 entity、沒有 checkpoint 或上傳包的檔案路徑；依賴它，錯的方向正好是把有用的檔說成沒被引用。索引檔本身歸 `rebuildable`。

走法失敗（run 卡不是 UTF-8、讀不了、schema 壞掉等）記進 `skipped`、WARN：gc 的容忍比 backup 寬，每個走法單位（一個 run、一個 dataset 的自有檔、一個預登記、一個 submission、一個 `image_root`、一份 backup 清單、一個產物）各自為交易，失敗就整批丟掉，不會留下「已被 skip 的 submission 仍掛在別的檔上當引用者」；接 `VcpError`、`OSError`、`ValueError`，其他例外是程式錯誤，照舊 ABORT。記錄說有、磁碟上沒有的路徑只計數（`missing=`），不 WARN：刪掉本機副本、只留遠端是正常的。

### 類別

每個檔依序套用，第一條成立的就是它的類別：

| 順序 | 類別 | 條件 |
|---|---|---|
| 1 | `protected` | data root 的 `raw/`、`locks/` 底下；任何根裡的 `.git` 目錄底下 |
| 2 | `debris` | 檔名以 `.tmp` 結尾（不分大小寫）；有 `spec.json` 沒有 `manifest.json` 的半途產物目錄裡的檔 |
| 3 | `referenced` | 這個檔或它的上層目錄被上表的任一來源引用 |
| 4 | `rebuildable` | `datasets/<name>/cache/materialize/` 底下（`vcp data materialize` 重建）；`cache/audit/` 與 `cache/dhash.jsonl`（`vcp data audit` 重建）；`indexes/` 底下（`vcp provenance rebuild` 重建） |
| 5 | `record` | vcp 自己的版面、但沒有任何引用走到：走法失敗（`skipped`）的 run 的 `runs/<id>/`；`runs/<id>/inputs/`（`eval ingest --keep-input` 留的來源副本，run 卡沒有欄位記它）；有 `manifest.json` 的產物目錄與 `artifacts/<kind>/supersession.jsonl`；`measure/`、`submit/`、`logs/`；`datasets/<name>/` 的 `samples.jsonl`、`raw_manifest.txt`，與 `cache/` 底下其他的檔（例如 `import_skipped.jsonl`）；`--root` 涵蓋到的 configs root |
| 6 | `unreferenced` | 其他（含 `artifacts/<kind>/` 底下兩個檔都沒有的外來目錄、沒有 `run.yaml` 的 `runs/<x>/`、走得到的 run 目錄裡沒有任何紀錄提到的檔） |

- `protected` 排第一：`raw/` 照鐵則永不動，即使裡面有 `.tmp`。
- `record` 不是垃圾：那是 vcp 的紀錄，只是沒有結論再依賴它（例如別的 checkout 的 dataset、被放棄的 run）。要不要整批放棄是人的決定，vcp 不說它可以刪；刪之前先問自己是否放棄那個 dataset 或 run。
- `unreferenced` 只表示「vcp 的紀錄沒提到」，不表示沒有別的東西需要它（筆記、notebook、別的工具、共用 data root 的別的專案）。每次輸出的最後一行都這樣說。

### 項目與單位

項目是一個檔，或一個目錄：目錄底下每個檔的（類別、引用者、`copy`）都相同時，往上合併成一項，但不超過「單位」；含有被略過部分（符號連結、junction、讀不了的項目）的目錄不合併，因為那一項會蓋住沒看到的檔。

| 位置 | 單位 |
|---|---|
| `raw/<name>/…` | `raw/<name>` |
| `datasets/<name>/cache/materialize/<mode>[-r<長邊>]/…` | 那一個模式目錄（`png` 與 `npy-r256` 是兩項） |
| `datasets/<name>/cache/` 底下的其他項目（`audit/`、`dhash.jsonl`、`import_skipped.jsonl`…） | `cache/` 的直接子項 |
| `datasets/<name>/` 的其他 | `datasets/<name>` |
| `runs/<id>/…`、`measure/<name>/…`、`submit/<test>/<id>/…` | 那一層 |
| `artifacts/<kind>/<id>/…` | `artifacts/<kind>/<id>` |
| `artifacts/<kind>/`、`submit/<test>/` 直接底下的檔（`supersession.jsonl`、共用台帳） | 檔本身 |
| `indexes/`、`logs/`、`locks/`、data root 的其他頂層項目 | 那個頂層項目 |
| `--root` 底下 | 根的每個直接子項 |
| 檢查點目錄（不遞迴） | 每個檔 |

位元組 `>= --min-mib` 的項目才列出，依位元組由大到小、同大小依路徑排序。`copy`：被引用的 checkpoint 有 `train upload` 驗過的副本時，記那個目的地；backup 推過的副本不逐檔判斷。

**重複檔**：類別是 `record` 或 `unreferenced`、大小 `>= max(1 MiB, 門檻)` 的檔，大小等於某個「有記錄 sha」的被引用檔（checkpoint、產物檔、stage 的上傳檔、預測檔）時才雜湊；sha 相同、而且原件還在磁碟上（原件也雜湊一次確認它仍是那些位元組）→ `duplicate_of` 記那個被引用檔的路徑。只雜湊大小相符的候選，所以量以候選為界；逐位元相同的權重複本認得出來，打包成 zip 的認不出來。目錄項目記 `duplicate_bytes`。

### 輸出

人看的行，每項一行：`<類別> <大小> <路徑>[/ (files=<n>)] [by <引用者>; …; +<k> more] [copy <dest>] [duplicate of <path>]`；大小 `>= 1 GiB` 印 GiB、否則 MiB，都無條件捨去到一位小數，引用者最多印三個。接著每類一行總量（`<類別>: <大小> in <n> files`）與 `duplicates:`，再來是 `skipped:` / `unreadable:` / `running:` 各行，最後一行：`gc scan <id>: listed only; vcp deletes nothing. unreferenced means no vcp record names it, not that nothing else needs it`。

`--json` 的 result 是 `scan.json` 加上 `items`（全部列出的項目，每項 `path` `kind` `bytes` `files` `class` `referrers` `copy` `duplicate_of` `duplicate_bytes` `mtime`）；`scan.json` 裡的 `items` 只是個數。

VERDICT（OK / WARN exit 0、FAIL 1、ABORT 2）：`scan=<id>|none` `roots=`（實際掃的根數：data root、檢查點目錄、`--root`，`resolve()` 後去重）`root_options=`（`--root` 的個數）`items=` `min_mib=` `referenced_gib=` `record_gib=` `rebuildable_gib=` `debris_gib=` `unreferenced_gib=` `protected_gib=` `duplicate_gib=` `missing=` `skipped=` `unreadable=` `running=`。後三項任一 `> 0` → WARN；找到 `debris` 或 `unreferenced` 是這個命令的本分，不 WARN。FAIL：`invalid:`（`--min-mib`）、`not_found:`（`--root`），失敗的 VERDICT 只帶已知的 `min_mib=`（有給時）與 `root_options=`（有給 `--root` 時），不帶 `roots=`；寫產物失敗 → ABORT（原例外）。沒有新的 `reason=` 字彙。

- `skipped > 0`：有引用沒讀到，它們引用的檔可能被說成 `unreferenced`；人看的行說是哪一個與原因。
- `unreadable > 0`：有目錄沒看到。
- `running > 0`：有 run 的最新 attempt 還是 `running`，它正在寫的檔還沒登記，會出現在 `unreferenced`。

### 稽核產物 `artifacts/gc_scan/<id>/`

掃完之後才開（掃描中途失敗不留半途目錄），id 是 `gc-<YYYYMMDDTHHMMSSZ>-<8 位十六進位 nonce>`；`spec.json`（`kind=gc_scan`、`params`：`min_bytes`、`root_options`，沒有 `inputs`：為了 input 雜湊整個 data root 不划算）、`scan.json`、`items.jsonl`（每個列出的項目一行，同 `--json` 的 `items`）、`manifest.json`（commit 點）。`scan.json`：`scanned_at`、`finished_at`、`data_root`、`configs_root`、`roots`（每項 `path`、`recursive`、`source=data_root|checkpoint_dir|option`）、`min_bytes`、`totals`（每類 `bytes`、`files`）、`duplicates`、`items`（個數）、`references`（讀了幾個 run、dataset、backup 清單、產物）、`missing`、`skipped`、`unreadable`、`running`。路徑一律 `store_path`：data root 底下是相對路徑，其他是絕對路徑。產物在 data root，不進 git；它會被 `artifact status` 列出、被 `provenance sync` 當成一般產物，之後的掃描裡它自己算 `record`。真資料的整合測試不跑 `gc scan`（它會寫產物，而 `raw/` 與真的 data root 不能多任何東西）。

### 已知限制

- 只知道 vcp 自己的紀錄。`unreferenced` 不等於可以刪；別的 configs root 的 backup 清單與預登記不會讀到（它們的 run 目錄有走到）。
- 不知道平台上的副本（例如 Kaggle dataset）；backup 推過的副本不逐檔判斷，只有 `train upload` 驗過的 checkpoint 有 `copy`。
- 不跟隨符號連結與 junction；硬連結會被算兩次；經由連結路徑寫下的引用可能對不到掃到的檔。
- 重複檔只認位元組完全相同、而且被引用的那一份有記錄 sha 的；壓縮或重新打包過的認不出來。
- 只以 sha 記的權重（`eval ingest --weights` 的 `weights_hash`、kernel 提交的 `WeightRef`）沒有路徑，不算引用、也不參與重複檔比對：不經 `vcp train run` 登記的權重會出現在 `unreferenced`。
- 快照不上鎖：正在訓練時新寫的 checkpoint 還沒登記（所以 `running > 0` 時 WARN）。
- 很大的 `--root` 會掃很久，沒有進度輸出；每次掃描留一個小產物。

## 程式碼快照命令 `vcp code`

0.18.0 起。`train run` 每個 attempt 自動做快照（見上面的「程式碼快照、追蹤與授權」）；`vcp code` 是給 `train run` 以外的地方用的：kernel 的 bundle、外部訓練、benchmark，以及事後驗證與比較。

| 命令 | 作用 | 主要選項 |
|---|---|---|
| `vcp code snapshot` | 對每個 `--root` 寫（或找到已經寫好的）`code_snapshot` 產物，依序印每個 root 的 id。新寫的快照**保留全部位元組**（不設單檔與累計上限，雜湊上限照舊；範圍靠 `--root` 與 `.gitignore`）。同內容已經有一份（例如 `train run` 先寫了有上限的）→ 重用，`not_kept=<n>` `> 0` → WARN。明要的快照沒有降級：`too_large:`、`drift:`（掃描後被改）、`not_found:`（不是目錄）、`invalid:`（`--root` 在 data root 或 configs root 裡面，那裡一個檔都不會納入）是 FAIL，`locked` / `partial` / `unwritable` / `unreadable` 是 ABORT `code_unavailable:`（`code_root=<label>` `cause=`）。VERDICT `roots=` `ids=` `files=` `kept=` `not_kept=` `reused=`；失敗的 VERDICT 帶 `root=`（所有 `--root`）與 `code_root=` | `--root DIR`（必填，可重複）、`--json`、`--data-root`、`--configs-root` |
| `vcp code verify` | **`--id`**：這份快照還成立嗎——產物完好、`index.jsonl` 跟保留的檔一致、身分重算相同 → OK；否則 FAIL `mismatch:`（`mismatch=` `missing=`）。**不看目前的工作樹**：程式碼漂移了，舊快照照樣驗得過。**`--dir`**：驗 `vcp code export` 寫出的目錄，不需要 git 或原 repo；`DIR/.vcp-code/` 的身分要能由 index 重算，VERDICT 的 `id=` 是這個目錄「是哪一份快照」（`code-<身分前 16 碼>`），同時給 `--id` 就必須是它，否則 FAIL `mismatch:`。在場的檔一律要跟 index 的 sha 相同；`kept: true` 的檔不在 → FAIL `mismatch:`（`missing=`）；`kept: false` 的檔不在 → WARN `not_kept=<n>`；index 以外、符合規則的檔 → WARN `extra=<n>`；index 路徑上的連結（symlink）一律 `mismatch:`、從不跟隨。VERDICT `id=` / `dir=` `files=` `kept=`（`--dir` 另有 `not_kept=` `extra=`） | `--id`、`--dir`（兩者至少給一個）、`--json`、`--data-root` |
| `vcp code diff` | 拿快照跟**目前的檔**比（同一套規則與上限，只看 index、不碰快照的位元組）：`changed=` `added=` `removed=`，任一 `> 0` → WARN；唯讀。這是「目前的 checkout 漂移了沒」，跟 `verify` 分開。`--id ID --root DIR` 比一份快照與一個目錄（只排除 data root 與現在這個 configs root，不知道快照當時排除了哪些 checkpoint 目錄，所以快照時排除的目錄裡若有 `CODE` 檔會被報成 `added`；巢狀 root 的檔同理）；`--run R [--attempt N]` 比那個 attempt（預設最後一個）每個 root 的快照與它現在的路徑，並套該 attempt 的 `env.<n>.json` 記下的 `code.excluded_dirs` 與巢狀 root（另給 `roots=`），不能跟 `--id` / `--root` 混用 | `--id` + `--root`，或 `--run` [+ `--attempt`]；`--json`、`--data-root`、`--configs-root` |
| `vcp code export` | 把快照保留的檔寫到 `DIR/<path>`，index 與 `snapshot.json` 寫到 `DIR/.vcp-code/`；沒有保留位元組的檔不寫，WARN `not_kept=<n>`。`DIR` 已存在且非空 → FAIL `exists:`，在 data root 裡 → FAIL `invalid:`。VERDICT `files=` `exported=` `not_kept=`。沒有任何命令把快照寫回工作樹 | `--id`、`--out DIR`（皆必填）、`--json`、`--data-root` |

所有 `code *` 命令以 VERDICT 收尾（OK / WARN exit 0、FAIL 1、ABORT 2），`--json` 時結果到 stdout、VERDICT 到 stderr，永不提問；失敗的 VERDICT 帶已知的 `id=` / `root=` / `run=`。新 `reason=` 字：`too_large:`、`code_unavailable:`（ABORT）；其餘沿用 `drift:`、`mismatch:`、`not_found:`、`exists:`、`invalid:`。

### 快照裡有什麼（`vcp.code.rules`，`rules: 1`）

原則：**訓練的輸出不是程式碼身分**。框架會把 `args.yaml`、`hparams.yaml`、`config.json`、`metrics.json` 寫進 `--cwd`；算進去的話，benchmark 自己的輸出就會改掉正式 run 的快照 id，授權的比對與重用都失效。規則固定、不給設定：

- **跳過，不讀也不列**：任何一段以 `.` 開頭的路徑（`.git`、`.venv`、`.env*`、`.claude`、`.hydra`…）；`__pycache__`、`node_modules`、`site-packages`、`*.egg-info`、含 `pyvenv.cfg` 的目錄；data root 與 configs root 底下的一切；屬於其他 root 的檔（一個檔只屬於最內層的 root）；`train run` 的 `--checkpoints` / `--final` 每個 glob 的基底目錄（第一個含 `*`、`?`、`[` 的路徑段之前的目錄部分，以 `--cwd` 為基準；基底是某個 root 本身、它的上層或底下有巢狀的 root 時不排除任何東西）；生成程式碼登記表以環境變數指到 root 之內的位置；symlink 不跟隨。
- **兩組副檔名**（不分大小寫）：程式 `CODE` = `.py .pyi .pyx .pxd .c .cc .cpp .cu .cuh .h .hpp`；設定與建置 `CONFIG` = `.pyd .so .ipynb .sh .ps1 .bat .cmd .toml .cfg .ini .yaml .yml .json`，以及檔名 `requirements*.txt`、`constraints*.txt`、`*.lock`、`Makefile`、`Dockerfile`。兩組都不在的（`.md`、其他 `.txt`、`.csv`、圖片、資料）不讀。
- **git root**（在 root 目錄跑 `git ls-files -z --cached --others --exclude-standard`）：追蹤檔 `CODE` 與 `CONFIG` 都納入，位元組是工作樹的現況（HEAD 加上 dirty 的差異）；**未追蹤、未被忽略的檔只納入 `CODE`**（未追蹤的 `.yaml` / `.json` / `.ipynb` / `.so` / `.sh` 從不開檔）；被忽略的檔永不讀；追蹤但已刪除的不列；submodule 不展開（要涵蓋就用 `--code-root`）。有 `.git` 項目、但 git 問不動（沒裝、dubious ownership）的樹仍視為 git root、掃描 fail closed 成 `unreadable`，不退回「目錄 root」去讀被忽略的檔。
- **一般目錄 root**：沒有「追蹤」可分，全部比照未追蹤，只納入 `CODE`。
- **機密檔名**（不分大小寫）：`*.pem *.key *.p12 *.pfx *.jks *.kdbx id_rsa* id_ed25519* id_ecdsa* kaggle.json rclone.conf pg_service.conf pgpass.conf _netrc credentials* *secret* *service-account* *service_account*` → 不開檔、不雜湊，只把路徑記進 run 端的 `excluded_paths`。寫死在程式碼裡的機密 vcp 不掃（會把每個 sha 常數都當機密），它會跟著程式碼進 data root 與備份（tier 2，含異地）：機密放環境變數或憑證檔。
- **身分與保留**：身分 `sha256("vcp-code/1\n" + 依 path 排序的每個檔一行 "<sha256> <bytes> <path>\n")`，`kept` 不進身分；id 是前 16 碼 `code-<16 hex>`，root 的 label、路徑、commit 不進產物。`snapshot.json` 不含時戳、版本與保留統計，所以同內容在任何機器、由誰寫，位元組都相同（授權比對它的 sha）。保留位元組：`train run` 單檔 ≤ 1 MiB 且這個 root 累計 ≤ 64 MiB（依 path 順序貪婪，之後較小的檔仍可放進）才保留，其餘只記 sha；`vcp code snapshot` 全保留；同一個內容只有一份產物，誰先寫就是誰的保留方式。
- **上限**（每個 root）：納入 ≤ 20,000 檔、雜湊總量 ≤ 512 MiB、一般目錄走訪 ≤ 200,000 個項目；超過 → 這個 root `too_large`，不寫快照。
- **Windows**：保留位元組時，路徑（含寫入用的暫存檔名）超過 `MAX_PATH`（259 字元）的 root 記 `unwritable`——這個預檢**照樣適用**於 `LongPathsEnabled=1` 的機器；只差大小寫的兩個檔也記 `unwritable`（各平台都是，免得在大小寫不分的磁碟上寫到一半才失敗）。預檢不過時什麼都不寫。訓練 venv 裡 editable 的 vcp 是整個 checkout，data root 路徑太長時它會是 `unwritable` 的 root、run 降到 `declared`；用短的 data root（例如 `C:/vcp-data`）。
- **跨作業系統的身分**：Windows 上 `core.autocrlf=true` 的 checkout 是 CRLF，跟 Linux 上同一個 commit 的身分不同，建議 `.gitattributes` 設 `eol=lf`；各機器的全域 git exclude 也會讓列出的檔不同。

### `verify` 與 `diff` 的分工，與 `export` 的來回

歷史可驗與目前漂移是兩個問題：`verify --id` 只看產物自己（程式碼之後怎麼動，舊快照照樣驗得過），`diff` 只看工作樹（不碰快照的位元組）。沒有原 repo、commit 被改寫、機器回收之後，用 `export` → 搬走 → `verify --dir` 還原並驗證：

```bash
uv run vcp code snapshot --root projects/D --root ../shared-lib       # 寫或重用；印每個 root 的 id
uv run vcp code verify --id code-0123456789abcdef                     # 產物自己還成立嗎（不看工作樹）
uv run vcp code diff --run y12x_r2                                    # 那個 run 的程式碼，現在的檔動了沒
uv run vcp code export --id code-0123456789abcdef --out D:/bundles/code-D
uv run vcp code verify --dir D:/bundles/code-D [--id code-0123456789abcdef]   # 不需要 git 或原 repo
```

有上限的快照（`train run` 先寫的）`export` 後 `verify --dir` 是 WARN `not_kept=<n>`、exit 0；把缺的大檔照 index 的路徑手動放進去就照 sha 驗。在 Kaggle kernel 裡驗要裝 vcp 跑 `code verify --dir`；`index.jsonl` 是純 JSONL 加 sha256，日後可補一個只用標準函式庫的腳本。

### 稽核產物 `artifacts/code_snapshot/<id>/`

`snapshot.json`（`{schema_version, rules, identity_sha256, files, bytes}`）、`index.jsonl`（每個納入的檔一行 `{path, sha256, bytes, kept}`，依 `path` 排序）、`files/<path>`（`kept: true` 的原始位元組）、`manifest.json`（commit 點）。寫入前持有 `<data_root>/locks/code_snapshot-<id>.lock`（等 60 秒 → `locked`）；已 commit → 重用；目錄在、沒有 `manifest.json`（半途）→ 這個 id 寫不了（`partial`），留到 `vcp artifact clean`，不做重開的例外。同 id、不同身分 → `mismatch:`，不做 supersedes：搬走目錄再快照。儲存：每種不同的 root 內容存一份完整副本，跨快照不去重。`artifacts/code_trace/<run>-a<n>-t<seq>/trace.json` 記 `roots`、各分類的 `counts`、`generated_by`、`outside` / `unlisted` / `changed`（各 ≤ 50）與 `complete`。

## 不可變產物命令 `vcp artifact`

| 命令 | 作用 | 主要選項 |

| `vcp artifact create` | 把既有檔案封成一個產物：`<data_root>/artifacts/<kind>/<id>/`，`mkdir` 獨佔搶 id，逐檔 `.tmp → fsync → replace`，最後寫 `manifest.json`（有它才是產物）；`--input` 在 open 與 commit 各雜湊一次（變了 → `drift:`）；名稱 `code_snapshot.<label>` 與 `authorization` 的 input 是保留的（0.18.0：在 `mkdir` 之前檢查、被拒時什麼都不留，commit 再檢查一次；失敗字 `not_found:` 路徑形狀不對、`mismatch:` 快照壞了、`unauthorized:` / `superseded:` 授權不符，見「授權」）；`--id-pattern` 的具名群組必須等於同名欄位（`seed` / `dataset` / `plan_id` / `--param` 的鍵） | `--kind`、`--id`、`--file PATH\|NAME=PATH`…、`--dataset`、`--plan`、`--seed`、`--param k=v`…、`--input name=PATH`…、`--supersedes OLD --reason R`、`--id-pattern RE`、`--notes` |

| `vcp artifact lineage` | 根 → id → 接替者；`heads=` 是沒被接替的末端，`forks=` > 0 → WARN（唯讀） | `--kind`、`--id` |
| `vcp artifact status` | 每個 kind 的 `complete=` / `partial=`（有 `spec.json` 沒 manifest；附 `opened_at` 與 `failure.json` 的例外類別）/ `unlinked=` / `forks=` / `foreign=`（沒有 `spec.json` 的目錄，不碰）（唯讀） | `--kind` |

### 授權 `vcp artifact authorize`（0.18.0）

benchmark 證明了速度與正確性，正式 job 卻可能換了 dataset、ids、source audit、程式碼、batch 或模型，沒有東西會擋。授權把「benchmark 證明過的東西」記成一個 `authorization` 產物（`artifacts/authorization/<id>/authorization.json`，id 由人取），正式 job 消耗它時每一項都要一樣。vcp **不判斷 benchmark 過了沒**：授權只記錄人的決定（`--reason`）與依據。

| 命令 | 作用 | 主要選項 |
|---|---|---|
| `vcp artifact authorize` | 從依據算出 claims，去掉 `--free` 的、加上或覆寫 `--set` 的，寫成授權。依據要存在、完好、沒被取代：產物依據不見 → `not_found:`、驗不過 → `mismatch:`、被 supersede → `superseded:`；run 依據要有 `train.yaml`（`eval ingest` 的 run 沒有 → `invalid:`）與一個 attempt、該 attempt 每個 root 都有快照與環境 `identity`（缺 → `invalid:`），快照、plan、證據產物不見 → `not_found:`。每個 claim 名稱都要在消費者的字彙裡，否則 FAIL `unbindable:`（列名稱，提示 `--free`）；`--free` 的名稱不在 claims 裡 → `invalid:`；claims 不能是空的、`--reason` 不能空（`invalid:`）；id 已用 → `exists:`。VERDICT `id=` `basis=` `for=` `claims=` `freed=`（失敗也帶 `id=` `basis=`） | `--id`、`--basis artifact:<kind>/<id>\|run:<id>`、`--for artifact\|train`、`--target-kind K`（`--for artifact` 必填）、`--free NAME`（可重複：依據有、刻意不綁的）、`--set NAME=VALUE\|NAME=@PATH`（可重複；`@PATH` 取檔案的 sha）、`--reason`、`--supersedes OLD`、`--json`、`--data-root`、`--configs-root`（只有 run 依據讀它：要 plan 檔的 sha） |

claims 是依名稱排序的字串；`authorization.json` 另記 `consumer`、`target_kind`（`train` 時是 null）、`basis`、`claims_sha256`、`freed`、`reason`；依據是產物時，它的 `manifest.json` 以 `basis` input 釘住（改寫 → 消耗時 `superseded:`）。字彙（消費者能檢查的名稱）：

| claim | `--for artifact`（取自 job 的 `ArtifactSpec`） | `--for train`（`train run` 第一次寫入前算出） |
|---|---|---|
| `dataset`、`plan_id`、`seed` | 同名欄位 | `--dataset`、`--plan`、`--seed`（沒給 seed 就沒有這項） |
| `param:<k>` | `params[k]`，任何鍵 | `param:samples_hash`、`param:trained_on`（排序、逗號）、`param:config_sha256`（沒給 `--config` 時是命令的 sha）、`param:command_sha256` |
| `input:<name>` | 每個 input 的 sha（`authorization` 本身除外） | `input:plan`（plan 檔的 sha）、`input:code_snapshot.<label>`（`snapshot.json` 的 sha：內容相同就相同，跨機器也一樣）、`input:evidence.<name>`（來源 sha）、`input:labels.<id>`（manifest sha） |
| `env:python`、`env:packages`、`env:gpus` | 沒有 | `identity` 的三欄（Python 實作／版本／平台、非 editable 套件的 `name==version record_sha256` 排序後的 sha、GPU 名稱） |

慣例的 input 名（建議、不強制）：`card`、`plan`、`ids`（job 要處理的 id 清單檔）、`source_audit`、`model`、`code_snapshot.<label>`；`ids` 之類是 job 自己宣告的，實際讀了什麼仍要看收據。run 依據用右欄：取它**最後一個 finished attempt**（沒有就最後一個）的紀錄；session 綁定的證據（`Session.attach_evidence`）與後來的 attempt 才綁上的 ref 不是 claim（`train run` 開跑前無從知道）。

消耗（`ArtifactWriter` 與 `train run` 共用 `consume`）：(1) 授權與依據要還成立——授權壞了、被取代、不見，或依據的 manifest sha 不等於釘住的、依據被取代或 run 的 `run.yaml` 不見，都是 FAIL `superseded:`（訊息說是哪一種）；(2) 消費者種類與 `target_kind` 要相符；(3) 授權的每個 claim，消費者都要有、值相同——不符 → FAIL `unauthorized:`，`differs=<名稱>`（訊息附兩邊前 12 碼）；消費者多出來的 claim 不管。授權**可以重複使用**：每個消耗者在自己的紀錄裡釘住它（產物：`authorization` input；run：`authorization` ref），provenance 圖列得出所有使用者；條件全同就是同一個被證明過的設定，job 崩了不用重做 benchmark。**撤銷 = 用新的授權 supersede 它**（`--supersedes OLD`）；沒有時效、沒有次數上限。

```bash
# benchmark 是一個 ArtifactWriter 寫的產物 benchmark/b-50；人看過速度與幾何之後
uv run vcp artifact authorize --id full-extract-ok --basis artifact:benchmark/b-50 --for artifact --target-kind features \
  --free param:limit --free input:ids --reason "50 筆 benchmark：速度與幾何都過"
# 正式 job 的 spec 加一個 input：vcp.artifact.authorization.authorization_input(data_root, "full-extract-ok")
# benchmark 是一個 train run：之後的正式 run 帶 --authorization，第一次寫入前就比對
uv run vcp artifact authorize --id full-train-ok --basis run:bench-50 --for train --free param:trained_on --reason "…"
uv run vcp train run --run full --authorization full-train-ok … -- <訓練命令>
# 換了 dataset、程式碼、batch 之類 → FAIL unauthorized: differs=<那一項>，一個檔都沒寫
```

- **`train run --authorization`**：比對在第一次寫入之前（`vcp_mismatch:` 之後、磁碟檢查之前），不符 → FAIL `unauthorized:`（VERDICT `authorization=` `differs=`）；授權或依據不成立 → FAIL `superseded:`（VERDICT 仍帶 `authorization=`）。授權綁了某個 root 的快照、而那個 root 在掃描時失敗（`too_large` / `unreadable`）→ 那個 claim 缺 → `unauthorized:`。`--resume` 的每個 attempt 各比對一次，要重複 `--authorization`、也要重複 `--evidence` / `--labels`（它們是 claim 的一部分）；只比對開始時，中途的程式碼變化由 `code_changed` 與等級反映，不回頭作廢。**沒給 `--config` 時 `param:config_sha256` 是命令的 sha**，所以只放行 `param:command_sha256` 並不允許「多跑幾個 epoch」——兩項都要 `--free`，或改用 `--config` 把會變的參數放進設定檔。
- **產物 job**：`vcp.code.process.snapshot_inputs(data_root, extra_roots=())` 在同一個程序裡取得快照並回傳 `code_snapshot.<label>` 的 `InputRef`（root 規劃同 `train run`：`cwd` 是 `Path.cwd()` 所在的 repo，`script` 是 `__main__` 的檔，加 editable 與 `extra_roots`；保留上限同 `train run`；沒有降級，`too_large:` / `drift:` 是 FAIL、`locked` / `partial` / `unwritable` 是 ABORT `code_unavailable:`）。`ArtifactWriter` 在 `create` 與 `commit` 都對 `sys.modules` 分類：`outside` 或 `unlisted` → FAIL `code_outside:`（列前 5 個路徑，訊息說加 `extra_roots`；`generated` 不算）；被 import 的檔 `changed` → `IntegrityError` `drift:`；沒被 import 的檔改了不影響。別的程序取得的快照（例如 `vcp artifact create --input code_snapshot.cwd=PATH`）只做靜態檢查：路徑形狀對、產物完好。
- **已知限制**：快照在 import 之後、`snapshot_inputs` 之前才改的模組，磁碟上的位元組對得上、記憶體裡是舊的，這一關看不出來；授權不判斷 benchmark 的內容；重用的粒度是 root（同一個 root 裡沒被 import 的程式檔改了，新 spec 的快照就不同，`reuse` 報 `spec_mismatch:`，舊產物本身照樣有效）。

程式產生的產物走 Python API：

```python
from vcp.artifact.schema import ArtifactSpec, InputRef
from vcp.artifact.writer import ArtifactWriter
from vcp.core.paths import DatasetPaths

paths = DatasetPaths.resolve("knee")
spec = ArtifactSpec(
    kind="selection",
    id="six-slot-v2-s42",
    seed=42,
    id_pattern=r"six-slot-v2-s(?P<seed>\d+)",
    inputs=[
        InputRef(name="plan", path=str(paths.plan_json("fixed-v1")))
    ],  # 絕對路徑；相對路徑以 data root 為基準
)
with ArtifactWriter.create(spec, data_root=root) as art:
    art.write_json("receipt.json", payload)  # write_text / write_bytes 也有
    art.add_file("weights.pt", src_path)  # 串流複製並雜湊
    out = art.reserve("features.npy")  # 回傳最終路徑，自己用 numpy 寫；commit 時雜湊
    manifest = art.commit()  # 寫 manifest.json = commit；之後任何寫入 → closed:
```

`vcp.artifact.store.reuse(spec, root)` 只在完整 spec 逐欄相等（含每個 input 現算的 sha，`notes` 除外）才回傳既有 manifest，否則 `spec_mismatch:`——目錄存在不等於可重用。例外離開 `with` 會留下半途目錄與經 redact 的 `failure.json`；同一 id 不能再開，修正一律新 id + `supersedes`（open 查舊產物存在且已 commit，commit 驗逐檔 sha 並記其 manifest sha，之後 append `artifacts/<kind>/supersession.jsonl`）。manifest / `spec.json` / 台帳只含路徑、sha、大小、時戳、build string 與結構化參數——不放憑證。

## 匯入器與 `rows_read` 的語意

| 匯入器 | 來源 | `rows_read` 數的是 |
|---|---|---|
| `jsonl` | 已是標準格式的 `samples.jsonl` | sample 列 |
| `csv_boxes` | 一列一框的 CSV + 影像目錄 | CSV 資料列 |
| `coco` | instances JSON + 影像目錄 | annotations |
| `yolo` | `images/` + `labels/*.txt` + 類別表 | 影像 |
| `imagefolder` | `root/<class>/*` | 影像 |
| `image_csv` | CSV 路徑欄 + 標籤 / 目標欄 | CSV 資料列 |
| `dicom` | DICOM 目錄樹（header 分組） | 掃到的檔案 |

所有影像匯入器接受 `--opt exif=stored|oriented`（預設 `stored`），Orientation ≠ 1 的 view 會記進 `view.meta.exif_orientation` 並讓 VERDICT 帶 `exif_rotated=<n>` WARN；`materialize`（npy 與 png 皆然）是唯一會把方向烙進像素的步驟；`dicom` 匯入器不讀 EXIF。

## DICOM 形態的用法（以 RSNA Knee 為例）

200-study 影像基準的實際訓練、量測、融合、離線 notebook 打包、提交與備份命令見 [RSNA Knee RUNBOOK](../../projects/rsna-knee/RUNBOOK.md)。已實跑到本機 bundle；外部上傳與備份的待續條件也記在手冊。PyTorch 使用 `projects/rsna-knee/.venv`，Windows wrapper 後的訓練命令使用該 venv 的絕對 Python 路徑。

```bash
uv run vcp data import --importer dicom --src C:/vcp-data/raw/rsna-knee/train_series --name rsna-knee \
  --license "Competition rules" --url https://www.kaggle.com/competitions/rsna-knee-abnormality-detection \
  --downloaded-at 2026-09-03 \
  --opt labels_csv=../train.csv --opt "target_cols=ACL,MCL,Medial Meniscus,Lateral Meniscus,Medial OA,Lateral OA,PF OA,Effusion,Synovitis,Baker's,Contusion,Fracture" \
  --opt meta_cols=Report --opt seq_csv=../train_series.csv --opt "seq_cols=Fluid_Sensitive,Fat_Suppression,Anatomical_Plane" \
  --opt role_from=Anatomical_Plane --opt workers=8
uv run vcp data materialize --name rsna-knee --mode png --resize 256 --workers 4
uv run vcp data materialize --name rsna-knee --mode npy --stack-seq --workers 4
```

`sample_level=study|series`、`view_level=slice|series`、`group_from=<tag>`（預設 PatientID）、`glob=`、`tags=` 為其餘選項。快取在 `datasets/<name>/cache/materialize/<mode>[-r<長邊>]/`，`manifest.jsonl` 內路徑皆為相對路徑。
